# AMD hipVS HNSW 构建实验记录（2026-11-01）

本次真实 AMD 实例上的 SQL 验证完成：10000×128 数据的端到端构建中位数从 CPU 的 **2.623741 秒**降至 GPU 的 **1.020790 秒**，比值为 **2.570305×**。CPU Recall@10 为 0.953，GPU 三轮为 0.969、0.963、0.965；双方每轮实际 SQL 快照都保存全部 10000 个正确主键和逐字节一致的 FP32 向量。

控制器状态为 `PASS_LOCAL_VALIDATION_TARGET_UNSPECIFIED`，每组性能报告为 `MEASURED_TARGET_UNSPECIFIED`。这表示通过本次自定 0.95 质量门槛和功能检查，**不表示已通过赛事评分或达到尚未公布的官方目标**。小规模 200×16 组的 GPU 中位数更慢，只有 0.862360×，下文保留全部结果。

## 实现与版本

`LIB=HIPVS` 显式选择 FP32/L2 普通 HNSW 快照构建：GPU CAGRA 构建底层图，CPU 完成上层 HNSW，验证全部导出节点、邻接、向量和 VID 后导入 VSAG。查询与持久化使用 VSAG。缺少 GPU、桥接库或不支持的非空批次明确失败，不把 CPU 回退计为 GPU 构建。

## 参数、计时与复现

性能组使用 10000 个 128 维 FP32 向量、100 条查询、K=10、种子 20261031、批量导入 500 行。CPU/GPU 均使用 M=16、ef_construction=200、正式查询会话 ef_search=200，各运行三轮。双方正式 Recall@10 门槛固定为 0.95；性能目标未设置。数据指纹为：

```text
b35caa9beffe605b248289d7b21a6a29a5822673ccc8919ad4bf9d41e0aecae9
```

每轮使用新建表和索引；顺序为 CPU1、GPU1、GPU2、CPU2、CPU3、GPU3。端到端计时从原始数据已经准备完成、索引尚不存在时的 CREATE VECTOR INDEX 开始，到首条指定索引 ANN 查询完成，包含 GPU 传输、同步、转换、DDL 和首查询延迟。原始导入、正式质量检查及完整性校验另计。精确近邻真值由同一 FP32 数据采用 FP64 距离累加计算。

依赖准备与数据库构建步骤见 [README.md](README.md) 和 [桥接库文档](../../tools/hipvs_bridge_build/README.md)。在同类 AMD 工作区完成构建和 Python 依赖安装后，从本仓库根目录运行以下命令；输出目录必须尚不存在：

```bash
/workspace/amd-validation-python/bin/python unittest/amd_hipvs/run_cloud_validation.py \
  --workspace /workspace \
  --output /workspace/amd-validation-results-20261101-repro \
  --port 2883 --m 16 --ef-construction 200 --ef-search 200 --min-recall 0.95
```

控制器自行构建桥接库、检查 GPU 导出、启动固定资源的独立数据库，完成 SQL 生命周期和两种规模的三轮比较。上述复现路径可按环境安装位置调整，参数和计时方式不应更换后仍称为本次实验。

## 10000×128 全部原始测量

来源：[完整 JSON](results/20261101/build-10000x128.json)、[自动生成表格](results/20261101/build-10000x128.md)。表格按实际执行顺序保留；单位为秒。

| 路径 | 轮次 | 原始导入 | DDL | 端到端构建 | Recall@10 | 自身 ANN 命中（诊断） | 实际快照完整性 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| CPU | 1 | 0.723777 | 2.612263 | 8.105065 | 0.953 | 9983/10000 | 10000/10000，全部 FP32/ID 一致 |
| GPU | 1 | 0.723920 | 1.010340 | 1.019624 | 0.969 | 10000/10000 | 10000/10000，全部 FP32/ID 一致 |
| GPU | 2 | 0.713598 | 1.010195 | 1.020790 | 0.963 | 10000/10000 | 10000/10000，全部 FP32/ID 一致 |
| CPU | 2 | 0.717530 | 2.612916 | 2.623741 | 0.953 | 9983/10000 | 10000/10000，全部 FP32/ID 一致 |
| CPU | 3 | 0.710797 | 2.612418 | 2.620525 | 0.953 | 9983/10000 | 10000/10000，全部 FP32/ID 一致 |
| GPU | 3 | 0.714620 | 1.010106 | 1.021181 | 0.965 | 10000/10000 | 10000/10000，全部 FP32/ID 一致 |

CPU 第 1 轮显著较慢：DDL 约 2.612 秒，而首次可用查询把端到端时间延长到 8.105 秒。原始记录明确包含两次就绪重试错误码 `4016`；全部重试时间均保留在构建区间中。其他五轮没有就绪重试。本报告不删除该轮、不用 DDL 时间替换端到端时间，也不将其未被证明的内部原因归因于 GPU/CPU 算法。

- CPU 中位数：2.623740991577506 秒。
- GPU 中位数：1.020789746195078 秒。
- 中位数比值：**2.570305002922802×**，不是逐轮比值的平均数。
- 所有六轮均通过 0.95 Recall 门槛、指定向量索引查询计划和实际存储完整性检查。

## 完整性、生命周期及 GPU 证据

本地和真实 AMD 云端的 65 项 Python 单元/回归测试均通过。实际云端控制器完成桥接构建及 128×8、1000×32 GPU 导出检查，随后完成 SQL GPU CREATE、指定向量索引查询、数据库正常重启后的结果 ID/距离一致性，以及重启后的新增向量与删除验证。生命周期原文状态及实际查询计划保存于 [status.json](results/20261101/status.json)。

全部 12 个 CPU/GPU 性能和冒烟索引均直接读取本轮实际 SQL 快照和 VID→主键映射，核对全部节点、主键、FP32 向量和邻接范围。每轮 `storage_integrity` 保存完整计数、快照/映射 SHA256、准确辅助表和块键；不以 ANN 抽样或源表行数代替图完整性。

大数据 CPU 三轮各有 17 个输入向量未通过自身 ANN 诊断，即使诊断宽度提高至 10000、候选 K=1000，仍报告 9983/10000。实际 SQL 快照同时证明全部 10000 条向量和主键正确保存。正式 Recall 始终使用双方相同的 ef_search=200，未为提高成绩修改正式搜索宽度。独立原因诊断见 [native_cpu_diagnostic.md](native_cpu_diagnostic.md)，它不代替本次真实 SQL 证据。

每轮 GPU 记录保存真实后端完成日志：

```text

```

性能组 GPU1、GPU2、GPU3 的日志字节范围分别为 [9120,9294)、[9294,9468)、[9468,9642)，每段 SHA256 为 `9aefbf88a38c71c09c468d9cd6ebabbf0cb9d16c93fc70d17a8af08fd148b731`。相同文本产生相同哈希；不同字节范围与该独立实例每轮唯一表名/索引名共同关联本轮构建。原文、字节范围和来源记录均保存在 JSON 的 `raw_gpu_evidence`，没有手写成功事件替代后端日志。
