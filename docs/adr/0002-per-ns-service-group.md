# 后台服务 per-ns 实例化（否决全局队列 + ns_id 列）

多 ns 的后台服务（schema 刷新、plan cache、PX、DDL 调度等）有两种承载方式。我们选定**每个 `NamespaceRuntime` 持有一组 per-ns 服务实例**（构造即绑定 ns，模块内部保持单 ns 逻辑零感知），否决"全局一张任务队列 + ns_id 列"方案。

## Considered Options

- 全局队列 + ns_id 列：所有 ns 共享一套服务线程，任务带 ns_id。资源占用最优，但要改动每个模块的枚举、队列与调度结构，且让每个模块都感知 ns 身份——违反不变式 2b，复杂度不可控，否决。

## Consequences

- 代价是资源占用 = 活跃 ns 数 × 服务线程数。优化路径是 serverless 式休眠（冷 ns 停服务退线程留元数据，首访问毫秒级唤醒），而不是合并线程池。
- 线程池合并（共享 PX/timer 等）只作为后续按实测决定的备选；PX 池因任务闭包自带上下文，是共享化改动最小的候选。
