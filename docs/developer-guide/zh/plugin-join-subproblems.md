日期：2026-09-10。状态：本地串行连接子问题已接通并通过受控验证；

## 最新推进：局部相关关系（2026-09-10）

Rust v14 将局部关系策略扩展到两输入相关 SJC1 和多拥有者 SJD1。
三个策略共用关系外列检查：只有当前结果关系和所有保留输入都明确
判定 outside 的已解析列才能省略；参数来源仍必须映射到唯一合法
来源输入，不能把缺失/不确定来源当成无关数据忽略。

完整查询的关系贡献策略保留原来的全查询列要求。局部策略继续使用
宿主 v4 的完整参数交接与保留拥有者检查，不直接写任意 ParamStore。
上层原生算子可以继续使用局部输出中保留的隐藏列。

新增三表和四表 SQL，要求相关 Rust 子计划位于原生 HASH OUTER JOIN
下方。三表交接两个参数，四表合计交接五个参数；四表允许保留已
贡献的内层插件输入，再由外层插件接管另一组参数，而非强制展平为
同一种参考算法。用例核对正常规划/codegen、输出、完整参数映射、
第一次/第二次绑定后的取消及整体重扫。

二十一项参考插件单测已通过，含两输入/多拥有者的局部列保留、
未知依赖拒绝和绑定/宿主错误传播。生产目标检查通过（72974）。
首轮完整 kernel（76064）通过标量三表相关用例，四表已生成两个
嵌套 PLUGIN CUSTOM 与上层 HASH OUTER JOIN，并通过正常 codegen；

## 前一检查点：独立子问题接线（2026-09-10）

现有基础上新增独立 `optimizer.join.paths.v1` 路由：SDK 使用
`Registration::join_paths_hook` 注册，loader、server/provider 和
ObLogPlan 分开处理连接子问题、完整关系贡献及后期选择。新阶段沿用
v6 上下文，要求 builders、Around、一次 next，禁止 select。

每个查询块规划入口检查是否注册该 hook；没有注册则不为新阶段
提前构树。该检查不是整个规划过程的 registry epoch 快照；实际调用
仍使用 loader 的 lease 与 epoch 验证。

连接枚举在每次生成原生候选后提交当前关系尚未处理的本地串行
JoinPath。候选输入使用快照；原生路径一旦构树便不再回收复用。
插件贡献全部构造为独立 PluginPath 后才追加发布；失败回收暂存
路径且不标记输入已处理。相同输入不重复贡献；新分解产生的新路径
仍会进入下一次回调。已发表的插件路径不递归触发同一阶段。

Rust 参考插件 v13 新增独立子问题策略，保留完整关系多层相关策略。
部分关系仍读取全查询已解析列，只有根和两个输入都判定 outside 的
列才省略；归属不明则拒绝，不改变原查询列 API。当前新策略贡献
独立整数 INNER JOIN，不把完整关系参数交接策略直接用于部分关系。

新增受控三表 SQL 用例要求内层 Rust 实现与上层原生 LEFT JOIN
组合，并与纯原生结果比较。另有禁用快路径、独立路由、整组发布、
失败重试、重复输入和缓存路径不回收夹具。下方“原基础验证状态”
保留先前检查点；最新接线结果如下，不混用不同阶段的测试记录。

## 原基础设计：从完整关系树贡献继续向前

以下保留独立 PluginPath 基础的历史记录。独立阶段路由、路径固定、
发布和三表 SQL 已按顶部说明推进；其余要求继续作为后续范围。

现有 relation.paths 阶段在连接路径枚举完成、逻辑树生成后贡献候选。
Rust 已能替代满足条件的多层相关 JOIN，但不能据此宣称能在每个
中间关系上贡献路径、再由上层原生 JOIN 组合这些实现。

下一阶段把自定义实现接入真正的 Path 层，而不是在更多调用点重复
执行原有后期选择 hook。已有 relation.paths 和 candidate.select
保持各自契约；新阶段需要独立注册、作用域及发布规则。

## 新增路径表示

新增内核 `PluginPath`，所属关系仍是普通 ObJoinOrder；实现类别不再
从关系的 ACCESS/JOIN/SUBQUERY 类型推导。八种内置路径判断排除
PluginPath，避免将它转换成错误的 AccessPath/JoinPath 等具体类。

路径借用同一 ObLogPlan 拥有的逻辑树，不另持模块 lease 或保存插件
调用期图 ID。初始化检查 plan/关系表集合、本地串行及有限非负代价
和基数，复制排序、位置、并发、流水线、ambient cardinality 及参数
约束。重新估价委托逻辑实现，不调用内置 JoinPath 算法成本模型。

`ObJoinOrder::add_plugin_path` 将已构造树作为实现路径加入候选列表；
现有 create_plan_tree_from_path 可直接取回它的逻辑树。新增夹具验证
具体类型、原生候选共存、参数约束/属性传递、重新估价及失败传播、
逻辑树复用和非法路径不发布。当前仅为宿主层验证，不是新的 Rust
子问题回调或正常 SQL 连接枚举端到端证明。

原生和插件路径暂不互相 skyline 剪除，因为原生 inner-path 谓词
下推还会复制具体 Path、丢弃缓存逻辑树再重建；该协议尚不能应用于
插件树。强制 inner-path 生成跳过插件实现、使用保留的原生替代。
这不是永久限制：后续需让插件明确承接外部参数与下推谓词，再开放
相应重建/重绑定，而非把插件树伪装成内置路径。

冗余谓词检查也不再假定关系第一个路径一定是 JoinPath；找不到原生
谓词树时保留谓词，不猜测插件内部语义。

## 下一步接线要求

1. 新 hook 在中间关系的候选生成后触发，仍为追加贡献，不强制选中。
   Rust 策略可贡献自己的实现，之后参与上层原生 JOIN 组合和成本比较。
   没有注册该 hook 时不能提前构造全部逻辑树，须保留原生规划的成本
   和生命周期；应在查询规划入口按注册状态决定是否启用新阶段。
2. 早期构造逻辑树会使原生 Path 更早被引用；必须审计现有 JoinPath
   回收复用，不能让已被逻辑树引用的路径改作另一个候选。
3. 同一关系可由多个左右划分生成；需要界定每次回调的输入集合，
   防止重复贡献、漏掉新候选或在遍历候选时修改正在遍历的数组。
4. 公开当前关系范围和所需列。全查询的 SELECT/列清单不能被默默
   改成部分关系清单；Rust 不应因遇到查询其他关系的列就全部拒绝，
   也不能把未知依赖当成无关列丢弃。
5. 发布前验证整个贡献集合，失败不发布部分候选；原生路径及共享
   逻辑子树在失败/未选中时保持可用。最终树再修复父指针。
6. 真实三表以上 SQL 要验证“子问题 Rust 自定义实现 → 上层原生
   JOIN → 正常 codegen/执行”，并保留现有完整关系多层 Rust 替代用例。
   另测同一关系多个分解、多个插件、取消、重扫、错误及参数清理。
