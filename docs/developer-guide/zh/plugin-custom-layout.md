# 自定义计划的显式表达式布局

状态：已接入代码，完整 kernel 验证通过。此协议推进的是正常 SQL
规划与执行之间的数据流，不仅是手工构造物理 spec。

## 插件声明什么

`custom_path_request_v2` 保留 v1 的单输入候选、执行服务、opaque plan、
代价和排序/阻塞属性，增加有序的输入和输出表达式 ID 列表。ID 来自
本次 candidate_context_v3 的规划图，不是列序号、SQL 对象 ID 或 C++
指针。Rust 对应 `Context::custom_with_layout(path, inputs, outputs)`。

- 输入列表：插件需要宿主从子计划提供的值，列表顺序就是传输列序。
  可以包含最终 SELECT 不输出的依赖，也允许重复输入。
- 输出列表：插件实际产出的表达式及传输顺序，不是最终 SELECT 列表。
  输出可以不是某个输入表达式，算法必须实现该表达式的 SQL 语义。
  一个表达式身份只能出现一次；重复 SELECT 列仍可引用同一结果槽。
- 两个列表各最多 1024 项；空列表明确表示零列，不表示继承子计划。
  常量、参数等非行级可写槽不能作为插件输出，输入仍可使用常量表达式。

请求通过既有 build 回调提交，struct_size 使用完整 v2 大小。宿主在
返回前复制/解析列表，逻辑计划只保留实际表达式引用，不保存调用期 ID。
物理计划仍使用正常表达式序列化及实现绑定，不保存插件函数地址。
旧 v1 请求继续表示原有全列等价路径。

## 宿主如何落实

`LogPluginCustom` 将输入和输出加入表达式收集。输入依赖要求在子计划
一侧产生，避免本节点在子计划已经消费完后才尝试计算输入。分配后，
插件输出标为已产生；投影裁剪根据显式输入保留子计划依赖，不从输出
表达式的原始参数反向猜测插件到底需要什么输入。

内核后续替换表达式时同步更新两份列表。替换合并了两个输出身份时
明确拒绝，不擅自删掉某个槽位或改变 opaque plan 中的列序号。

codegen 分别生成 input_columns 和 columns 及其类型、NULL、codec
绑定。插件输出作为本节点产生的值，不放回 SQL calc_exprs 重新执行
原表达式。输入 decode、输出 encode 使用各自绑定，沿用前一阶段的
独立执行布局。

最终输出与过滤表达式必须能由插件声明的输出及可独立计算的表达式
组成。缺少某列时明确报错，不能读取共享 SQL frame 中遗留的最后一个
子输入值。输入也必须能从子计划的输出计算。检查使用有界、去重的
表达式遍历；构造错误阻止候选发布，分配后的依赖错误阻止物理计划
生成，均保留失败而不是执行不完整的数据流。

## 自由度与语义责任

这个接口不把算法限定为投影或 spool。插件可以接收依赖值，使用自身
算法产生已声明的 SQL 表达式；请求本身不会告诉宿主如何实现函数。
宿主检查身份、数据流、类型表示与生命周期，native 插件作者仍负责
值语义、关系结果、排序声明与代价的正确性。

本文 v2 请求仍是一个现有候选之上的单输入关系等价节点。后续 v3
已将目标关系与输入子树分开，见[计划片段](plugin-plan-fragments.md)；
多输入 SQL 纵向验证、更完整的关系/执行位置契约、常量值/参数读取、
自定义 EXPLAIN、批量接口和跨进程/PX 重绑定仍属完整目标，不能以本次
有序列表接口代替。Rust candidate 默认 hook 暂时仍使用全列 spool。

当前查询块的完整 SELECT 目标现另由 v4 query/target 接入，同一 ID
可用于本布局；不代表任意子计划都能计算查询的聚合/窗口等目标。
接口及验证进展见[查询目标](plugin-query-targets.md)。

## 验证边界

SDK 测试核对 C/Rust v2 布局、重复输入、零列、重复输出/超限拒绝，
以及宿主返回错误、错误新增索引或不一致数量时不可吞掉失败。

kernel 夹具通过规划图解析真实表达式，核对 ID 列表复制、计算表达式
输出与输入可不同、输入缺失或未声明输出依赖的拒绝，以及非法请求。
正常 SQL 用例由明确的 C++ 测试策略通过公开 graph/build 回调提交三列
输入、两列输出的 SPJ1 请求，经过实际优化器、分配/裁剪/codegen 和
Rust spool 执行；它不是手工物理 spec，也不是已实现通用 Rust 优化
策略的证明。子表函数实际使用 Rust DSO，schema/session 仍有测试替身。

额外的派生表达式用例使用已知只产生正 ordinal 的表函数，因此测试
策略可以合法地以 identity 实现该关系上的 ABS(ordinal)。它检查这项
插件输出不在子计划 output 或本节点 calc_exprs 中，并核对最终 SELECT
值；不将这个受控正值策略称为通用 ABS 算法。

该用例暴露并定位了参考 spool 的元数据判断问题：BIGINT 输入报告
precision=-1，ABS 的 BIGINT 输出报告 precision=20，类型、编码、NULL、
collation 和 scale 都相同。显式 SPJ1 投影现在区分 builtin 整数的显示
精度与数值表示；不再仅因该字段不同而拒绝。SQL 类型、编码、scale、
NULL 与宿主数值范围检查保持不变；浮点、自定义逻辑类型及旧全列
spool 仍严格核对 precision。这不是允许 DECIMAL 缩精度或隐式类型转换。

最新结果以[实施进度](plugin-implementation-status.md)为准；基础协议见
[规划图](plugin-candidate-graph.md)和[自定义执行器](plugin-custom-executor.md)。
