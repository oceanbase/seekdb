下文 v8 验证记录保留其历史含义。

日期：2026-09-10。状态：Rust 算法、正常 SQL 策略夹具与验证断言已接入，
八项 Rust 插件单测及生产动态库构建/审计通过；完整 kernel 首轮

## 本次推进

此前 v3 fragment 已能把目标结果关系与多个输入 PlanId 分开，但完整
SQL 纵向用例只使用一个输入。本次使用正常解析/重写/优化的 INNER JOIN，
由受控规划策略提交两个子计划和各自依赖，执行算法来自实际 Rust DSO。
不通过手工物理 spec 代替这条 SQL 链，也不调用内置 join 完成算法。

必须区分语言分工：v8 正常 SQL 的选择策略为 C++ 测试回调，通过
公开 graph/query/build 接口工作；执行算法为 Rust。Rust SDK 的
`custom_fragment` 有独立请求/布局测试，默认 Rust candidate hook
仍是单输入 spool。尚不把它描述成通用 Rust join 优化策略。

## SJE1 私有计划

Rust candidate v8 在原执行 service 上增加 `SJE1` 格式：四字节 magic、
两路各一个 little-endian u32 键序号、u32 输出列数，再为每个输出
保存 `(输入编号, 输入列序号)` 两个 u32。键/列序号小于 1024，输出
最多 1024 列；输入编号只有 0 和 1。拒绝截断、尾随字节及越界值。
这是插件自己的算法参数，不是 SQL 表达式 ID 或宿主指针。

两个输入可有独立宽度、键位置和输出映射。第一次读取任何输入之前，
检查两路键与全部输出的 schema，包括后来发现为空的输入。

键只接受相同逻辑 ID、SQL 类型和编码的已知 builtin 整数契约（包括
既有 GIS scalar 兼容 ID），不将自定义类型的字节相等当作 SQL 相等，
也不处理浮点 NaN、字符串排序规则或隐式跨类型转换。整数解码使用
SDK Number，内部以 i128 保留 signed/unsigned 极值。NULL 键不匹配，
重复键产生全部匹配对。这里不是 NULL-safe equality、外连接或半连接。

输出从声明的左右输入列取值，独立校验逻辑类型、SQL 类型、编码、
NULL、collation、scale 和 precision。沿用整数显示精度与表示精度的
既有区分。输入 codec 解码与输出编码仍由宿主负责；算法不解释 LOB
locator、内核 Datum 或持久类型格式。

## 状态和资源

算法将两个输入复制为 owned 行后，以嵌套循环逐个输出匹配对。跨输入
回调不持有借用行；输出使用 owned 数据的当次借用，不预先展开可能
为平方级规模的结果集。它的 CPU 复杂度仍为 O(L×R)，不是已优化的
hash join 或 spill 引擎，不能作为默认生产性能策略。

两路输入共用 65536 行、约 16 MiB 的参考预算。输入读取和匹配扫描均
检查取消；输入错误不伪装成 EOF。失败后由 SDK/宿主游标保持失败状态。
rescan 释放两路行数组及其容量、清除位置，重新验证并读取输入；关闭
释放状态和已有 module lease。

## SQL 验证设计

正常 SQL 使用两个真实 Rust 表函数，并带 ORDERED 提示固定该受控策略
的左右输入角色。连接键使用整数取模制造重复匹配，另一组用 NULLIF
制造 NULL 键；SELECT 同时返回左右原始 ordinal，ORDER BY 二者，
检查完整结果对而不只比较总行数。

策略在[关系候选贡献阶段](plugin-relation-paths.md)匹配一个 INNER JOIN、
一个等值条件且没有额外过滤/启动条件的
目标。每个输入布局为 `[连接键, 原始 ordinal]`，共同输出为左右原始
ordinal。v3 目标仍为整个 join 的结果关系，不能误填成左子节点。
生成物理计划应有两个 child、offsets `[0,2,4]` 和 SJE1 私有参数。
保留原生关系候选，由正常排序规划和代价比较决定是否使用插件，不
移除 ORDER BY，也不在该阶段强制 select。

测试覆盖标量与 batch=3 的普通 SQL 计划，重复读取和重扫；另在第一次
输入读取后取消，再成功 rescan 并核对完整结果。物理夹具单独验证左空/
右空、右输入失败以及越界右键在任何数据读取之前拒绝。物理夹具不能
被当作空输入 SQL 优化策略的证明。

本轮完整 kernel 已通过四组正常 SQL 用例：SORT 保留，PLUGIN CUSTOM
有两个 FUNCTION_TABLE 输入；各组执行三个 pass，包括取消后的重扫，
检查左右完整结果对。十二组物理多输入用例和既有矩阵同样通过。
具体过程见实施进度。现阶段也不宣称实库 MVCC、
跨查询块、分布式/PX 或计划缓存重绑定已验证。

## 后续

和执行位置信息，不能只猜测 matched-build 枚举数值或假设所有 join
条件的参数顺序。继续完善多输入表达式分配/裁剪、空/NULL/失败语义、
算子成本和资源接口，并扩展跨查询块与分布式契约。catalog 实库事务、
类型/索引/恢复及 AI/轻量化仍是完整插件化目标的一部分。
