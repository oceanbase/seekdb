# 多输入计划片段：结果关系与数据来源分离

状态：版本绑定的构造协议、Rust SDK 和内核接线已实现，生产构建与
103 项 SDK 测试、25 项 doc-test 和完整 kernel 回归通过。
这不是完整 JOIN 优化策略或分布式插件计划已经完成的声明。

## 请求模型

`custom_path_request_v3` 扩展显式布局请求，区分两个概念：

- `v2.v1.v1.input_index`：被替代的等价候选结果。插件必须实现它的
  SQL 关系语义，并正确产生声明的输出表达式值。
- `input_plans`：真正交给执行器的输入 PlanId，有序且最多 64 项。
  它们来自当前规划调用，必须是目标候选中的互不重叠子树，并属于
  同一 ObLogPlan；跨查询块输入尚需额外的表达式/规划上下文映射。
- `v2.inputs` 与 `input_offsets`：每个输入独立的有序表达式依赖；
  offsets 有输入数加一项，首项为 0，末项为扁平表达式数量，各段
  单调不减、最多 1024 列。允许零列输入，允许单个输入内重复列。
- `v2.outputs`：插件实际产生的独立 SQL 表达式槽，最多 1024 个，
  身份唯一。常量和参数等非行级可写槽仍不能作为插件输出。

没有输入时 offsets 为 `[0]`。这是源算子的构造方式，不意味着结果
关系为空；例如某插件可能独立产生目标候选的结果。参考 Rust SMP1
算法对零输入返回空关系，只是该算法的行为，不是规划协议的定义。

宿主将 PlanId 解析成规划节点、表达式 ID 解析成表达式引用，并保存
偏移与私有参数；不把调用期 ID 存入物理计划。请求精确大小区分 v1、
v2、v3，旧宿主明确拒绝未知大小，不将新请求按旧字段静默执行。

## Rust 接口

SDK 提供 `candidate::FragmentInput { plan, expressions }` 与
`Context::custom_fragment(path, inputs, outputs)`。其中 `path.input`
表示目标结果候选，`FragmentInput.plan` 才是输入节点。

输入和表达式身份继续绑定当前调用生命周期，不能跨查询保存或跨线程
复用。SDK 检查输入数、逐输入列数、重复输入与输出；复制为临时 C
请求后同步提交。分区允许总列数超过 1024，但每个输入分别满足上限。
真正的子树归属、重叠与类型/表达式可用性由宿主验证，不由 Rust 用
整数 ID 猜测。局部检查与宿主错误都不能被插件吞掉后报告成功。

## 语义属性与执行位置

新逻辑节点的基数、宽度、常量、等价集、函数依赖、表集合和至多一行
属性来自被替代的结果关系，不来自第一个输入。例如，两个输入各一行
不能自动推导合并结果也至多一行。代价则为实际输入代价之和加插件
算子代价，重新估算时不假定任一输入与结果有一比一行数关系。

`PRESERVES_ORDER` 在 v3 中声明保持目标候选的排序，而不是第一路输入
的排序。插件不声明时清除排序及匹配信息。执行流水线根据实际输入与
插件阻塞属性推导。上述声明仍由受信任 native 插件对语义负责，内核
不能证明任意算法的关系等价性。

执行位置是独立字段。当前实现 `LOCAL_SERIAL`，要求目标和每个输入
都是本地或 match-all、并发度为 1。尚未实现的分布式/PX 情形明确
拒绝；这不是全目标的最终限制。后续需增加 exchange、分片、执行
位置与并发契约，而不能复制被移除节点或首个输入的分布式状态。

## 构造、选择与数据流

构造阶段先检查输入在目标中可达，且输入子树不重复、嵌套、相互重叠
或存在执行循环；校验遍历有节点数量上限。设置 child 时恢复原 parent，
不在构造失败或未选中时修改输入树的父指针。

最终选择先准备所有新建分支的边并完成验证和内存分配，然后统一提交
parent。此前仅沿单子节点链处理的方式不能覆盖多个新建分支。

表达式分配将各段依赖放到对应 child 的生产者；投影裁剪根据实际
child 的输出数组选择其依赖列表，不把全部分支混在一起。codegen
逐输入验证表达式闭包，生成扁平输入数组与 offsets。输出继续由插件
节点产生，不在 SQL 本节点中按原表达式重新计算，也不能读旧输入槽。

## 验证范围与下一步

SDK 新增受控宿主用例验证两路共 2048 个表达式、零输入、零列分支、
输入/列数超限、重复身份及宿主失败；C/Rust 布局测试包含新请求。

kernel 新增逻辑夹具检查两路不同输入的布局、目标关系属性、成本、
子树归属/重叠、非法偏移和失败后的父指针。正常 SQL 另通过 v3
fragment 请求走构造、选择、分配、裁剪、codegen 和 Rust DSO，当前
该纵向用例仍用单个输入，不能据此宣称多输入 SQL 纵向链路已验证。
上述夹具与正常 SQL 用例均已通过完整 kernel；后者覆盖标量与 batch=3
计划，并检查生成的 offsets、实际输出与 rescan。首次 kernel 编译因
夹具 PPDeps 缺少类名限定失败，修正后按原命令重跑通过。

下一步需要真正的多输入 SQL 策略与 Rust 算法组合，验证跨分支依赖、
空/NULL 输入和重扫，以及未选中候选的状态。继续扩大关系/位置协议、
常量与参数读取、批量与缓存/PX；catalog 实库事务、类型/索引/恢复、
AI 资源管理和轻量化仍属于同一完整目标。
