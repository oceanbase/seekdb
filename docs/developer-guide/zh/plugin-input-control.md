## 执行自由度

`custom_context_v3` 在 v2 schema 之后追加 `rescan_input(input_index)`。
插件不再只能单向消费各输入，可以独立驱动某个子计划重新执行。
宿主调用真正的 child operator `rescan()`，不替插件清空算法状态、
不重扫其他输入，也不要求重建整个自定义算子。

执行服务 minor=1 声明理解可选 v3 后缀。minor=0 服务继续收到 v1/v2
精确前缀；minor=1 也可能收到旧上下文。Rust `Executor::INPUT_RESCAN`
生成 minor=1，`Context::has_input_rescan()` 区分能力缺失与零输入；
缺少能力时调用返回 UNSUPPORTED_ABI，不伪造重扫成功。

重扫可以发生在首次读取之前、输入 EOF 之后或连续多次。仅允许在
本次 next 尚未 emit 时使用；输入序号必须有效。所有借用输入行在
回调后失效，Rust 方法以可变 Context 借用强制这一点。执行 schema
仍由宿主持有，不因重扫变成新的 schema。

宿主和 SDK 在重扫前后检查取消。状态码、数据库错误、异常或非法
EOF 均不能被插件忽略后转为成功。失败后游标保持不可继续执行，
只有成功的整个算子 rescan 才能恢复；selective rescan 不是错误恢复
接口。游标的 module lease 一直保留到 close，重扫不重新解析服务。

## 重扫与参数绑定不是同一个动作

本接口在子计划**当前参数环境**中重扫，不绑定、清空或恢复任何参数，
也不提供任意 query frame 写权限。上一轮 candidate v6 已公开 JOIN
持有的参数/来源关系，但尚未把这些关系交给自定义算子承接。

后续完整参数化执行仍需连接以下步骤：

1. 规划请求声明参数 owner、来源表达式/输入及被驱动的目标输入。
2. 宿主验证作用域和来源可用性，接入表达式分配、裁剪与 codegen。
3. 运行时绑定一组参数，然后重扫对应子计划；失败不能继续读取
   半绑定状态，结束和外层重扫必须遵守参数拥有权/恢复规则。
4. Rust 策略和算法实际接管相关 JOIN，以正常 SQL 验证结果、取消、
   多次重扫与生命周期，而不是仅在合成图中登记接口。

这仍是完整设计的一部分。本次没有把“能够重扫”改称“参数化 JOIN
已完成”，也没有移除现有对相关输入的策略回退。

## Rust SJR1：显式选择的流式参考算法

v11 执行服务新增 SJR1，采用与 SJE1 相同的键和输出映射字段，但执行
策略不同：保留当前左行，为每个非 NULL 左键重扫右输入，逐对比较并
输出。无需缓存整个左/右关系；保留的两行按同一 16 MiB 预算核算
数据及行/单元元数据，其他有界 schema/映射等开销仍存在。它没有
spill，也不是已经校准成本的生产 JOIN 算法。

算法在任何输入读取之前验证两路键/输出 schema，保持整数类型、NULL
和重复匹配语义。跨 next 保留左行时使用 owned 数据；匹配右行在 emit
前复制，因为 emit 是另一个会使输入借用失效的宿主回调。取消或失败
保留游标失败状态，整体 rescan 清理保留行。

**默认 Rust 规划策略仍提交 SJE1，不自动切换为 SJR1。** 重扫右输入
可能重新调用易变函数、数据源或远端服务，不能只因元数据支持 rescan
就推断结果可重复。选择 SJR1 的策略需要对重复执行的 SQL 语义负责。
新的参考算法不等于优化器已经证明任意输入可以反复执行。

输出、零列结果、空左/右输入，首行无需耗尽输入，右侧独立重扫次数，
重扫失败/取消后的错误状态及恢复、坏 schema 在读取前拒绝。子输入
和物理 spec 为受控夹具，执行器和 Rust 动态库是真实实现；本轮完整
kernel 通过（进程 50521）。既有正常 SQL SJE1 与原生相关 JOIN 的
十六组 SQL，以及类型/LOB/投影矩阵继续通过。这不证明普通 SQL 的
Rust 策略已经选择 SJR1，也不证明实库事务或跨进程 PX 支持。
