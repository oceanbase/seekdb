## 为什么需要独立绑定协议

`rescan_input` 只在当前参数环境重扫。删除原生 Nested Loop JOIN 后，
原本由该 JOIN 更新的执行参数也必须有明确 owner，不能让右输入使用
上一行、NULL 或悬空的参数。参数表达式图接口只描述关系，不完成绑定。

`custom_path_request_v4` 在 v3 片段后追加完整绑定列表，每项声明：

- `parameter`：当前规划调用中的执行参数表达式 ID。
- `source_input/source_column`：已声明输入布局中的来源槽。
- `target_input`：绑定后驱动的目标子计划。

Rust 使用 `Context::custom_bound_fragment(path, inputs, outputs, bindings)`。
需要 `Hook::PARAMETERS`，不是缺少接口时假装没有参数。请求按精确大小
识别；v4 是版本绑定的 Server-dev 契约，不是新增长期公共 ABI 承诺。

## 初版拥有权和数据流

宿主当前承接被替代根 JOIN 的完整 NestedLoop 参数列表，保留原左右
两子树，来源输入 0、目标输入 1；检查参数身份、重复项、来源表达式
与输入槽一致。above-pushdown 参数、任意删除子图及跨查询块拥有权
需要后续协议，不在初版中隐式猜测。

逻辑节点保存解析后的参数表达式和来源槽，接入表达式收集、改写、
裁剪与 codegen；物理 spec 使用正常动态参数 setter。调用期 ID 不
进入执行缓存。参数 store 必须按正常物理计划初始化流程预留。

每次成功读取左输入，宿主复制参数来源的物理 Datum 快照；参数值不
指向 Rust 输出 buffer，也不依赖另一输入读取后已经失效的行借用。
来源推进会清空旧绑定并使目标不可读取。快照 payload 合计限 16 MiB，
另有参数数量和布局上限；这不是所有执行内存已纳入统一租户预算的声明。

执行 `custom_context_v4` / service minor=2 追加 `bind_rescan_input`：
先将当前快照写入全部参数，再重扫目标子算子；成功后才允许读取。
允许针对同一来源行重新绑定，不开放任意 prepared/user 参数写入。
旧服务只收到自己的 v1/v2/v3 前缀；新服务也必须检查可选能力。

独立重扫目标输入仅在已有有效绑定时允许。后续新增来源输入的独立
重扫：执行重扫前清空来源快照、owned 参数并使目标输入失效；必须
重新读取来源行，再 bind-rescan 才能访问目标。允许在来源 EOF 后或
连续重扫，不把 rewind 当作已有来源行。整个算子重扫、close/destroy 清理
本节点拥有的参数、来源快照和执行状态；不改写不属于它的参数。

这使 Rust 算法能够自行控制来源重扫，不必为了重置一条输入而重建
整个算子。执行次数与易变性语义仍由插件负责；默认 SJC1 策略没有
因此改变为重复扫描左输入。来源重扫失败也不能复用旧参数环境。

绑定/重扫前后检查取消，失败不允许读取半绑定环境。宿主、loader
及 SDK 保持错误状态，被插件忽略的错误不能变成成功或 EOF；恢复
需要成功的整个算子重扫，不能只重扫一个输入来解除错误。

## SJC1：实际 Rust 策略和执行

Rust join-policy 对本地 INNER JOIN 读取 NestedLoop 绑定，只有来源
属于左输入、满足当前确定性条件，并且根已没有待处理 JOIN/filter/
startup 谓词时，才贡献 SJC1。保留子计划中的相关表函数和过滤计算；
插件不是绕过这些谓词直接产生笛卡尔积。

策略保存全部来源依赖与上层需要的查询列，去重并生成输出映射；
参考代价为 `1 + left_rows * right_rows * 0.02`，仍未生产校准。
SJC1 复用映射格式，两个键字段必须为零，不按整数键自行比较。

执行循环为：读取并拥有左行 → 绑定/重扫右输入 → 读取右行并产生
配对结果 → 右侧 EOF 后推进左行。NULL 来源不能像独立等值 JOIN
的 NULL 键一样被直接跳过，其行为由原子计划的 SQL 表达式决定。
跨宿主回调只保存 owned 行，输出前复制当前右行；沿用流式行预算，
取消、重扫和 module lease 契约。尚无 spill 或生产资源调度策略。

独立输入的 SJE1 策略和显式 SJR1 仍保留，不自动将所有独立输入改为
重复执行。支持重扫不等于易变函数、远端请求或其他输入能够语义等价地
多次执行。

失败，修正调用处后重新构建通过（16190）。完整 kernel（40271）通过：

schema/session 等仍有夹具，不证明实库 catalog 或跨进程 PX。

SDK 后续增加 v4 请求传输、绑定索引/重复/上限/能力、错误保持、旧
上下文和跨绑定借用的 compile-fail 检查，119 项测试与 27 项 doc-test
通过。首次 SDK 重跑遇到 LLVM 链接器崩溃；独立构建结束后重跑通过。
Rust 策略新增完整绑定映射、来源去重、不适用关系与宿主失败覆盖，

### 后续快照与来源重扫验证

两组新增物理用例随完整 kernel 通过（91380）：VARCHAR 与带 header
的 in-row LOB 参数，覆盖 NULL、空值、含 NUL/UTF-8 和 70 KB 数据。
测试在 Rust 已复制当前左行、实际绑定尚未发生时，改写来源数值及
字节缓冲区，之后由真实子算子检查参数 Datum 和 ParamStore；结果
仍来自宿主独立快照。NULL 来源仍驱动右输入，不按 NULL 等值键跳过。

两个参数共同绑定，第三个无关参数保留哨兵值；右侧绑定后 rescan
失败、整体 rescan 中兄弟输入失败、提前 close 及重开都检查清理、
错误保持和重新执行。以上为真实 Rust 算法/loader/物理算子与手工
子输入、spec，不等同于新增正常 SQL 或实库扫描验证。

来源独立重扫的宿主实现及测试已加入，生产重建通过（10949），
完整 kernel 再次通过（23099）：在已有
绑定的情况下重扫来源、EOF 后重扫、重复重扫与来源重扫失败，随后

算法；不声称默认 Rust 规划策略新增了来源重扫优化。
