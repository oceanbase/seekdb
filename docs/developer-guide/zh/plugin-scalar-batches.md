# 插件标量函数的真正批量调用

本节描述版本化 C ABI 与 Rust SDK 的批量函数协议，以及 SQL 执行接入。
这不是列式 ABI、异步模型调度器或零拷贝承诺。

## 1. 插件决定如何处理一批输入

`execution_spi.h` 在原有 function service 后追加 v3 后缀，保留单行入口，
增加 `execute_batch`。宿主按 `struct_size`、SPI minor 与保留字段检查后缀，
不会读取只提供旧 v1/v2 对象的内存。没有批量后缀的旧插件仍使用单行回调。

一次批量回调接收多个 `seekdb_plugin_batch_row_v1_t`。每行是一组带逻辑类型
身份的值，宿主完成已绑定的隐式转换；并非要求插件再次按 SQL 名解析函数。
同批行使用相同参数数量与有效类型。插件可以将整批输入交给模型或算法库，
不必为每行重复进入动态库。

结果用行索引提交，允许乱序；每个输入行必须恰好产生一个结果，包括 NULL。
缺行、重复、越界、类型不符、超限、错误或取消使本批失败，EOF 不是成功。
输入行上限为 1024，单值载荷上限 16 MiB，批量输入与输出各上限 64 MiB。
这些是同步传输载荷限制，不是插件进程全部内存、模型或 GPU 的资源预算。

## 2. Rust SDK

`seekdb_extension::batch::{Batch, Handler, Service}` 封装批量入口：

- `Handler::execute` 每批调用一次；`Batch::row` 借用读取该行参数。
- `emit_i64` / `emit_bytes` 用索引输出；校验结果数量和重复调用，保留宿主错误。
- `poll_query` 查询 deadline 与取消，错误保持到该批结束。
- `with_row` 可复用现有单行 Rust handler，并保留查询 SQL context。
- `Service::with_scalar` 同时提供批量函数和已有单行函数指针。

`Batch` 不能跨线程转移；参数、context 与返回值指针不得逃逸同步调用。
Rust unwind panic 在 C 边界转换为失败，但原生插件仍是受信任代码，不是沙箱。
需要异步模型调用时，必须另建拥有数据所有权的任务协议，不能保存这些借用指针。

## 3. 宿主结果与生命周期

loader 固定对象、实现和转换服务的 lease，再调用批量入口或旧单行回退。
整批结果先复制、校验和暂存，全部成功且通过取消检查后才交给 SQL 调用者。
插件在较晚的行失败时，不向调用者发布前面行的暂存结果。

如果调用者自己的结果转换/分配失败，可能已经收到一段输出，因此调用者仍
必须丢弃整个失败批次，不能消费前缀。外部请求、已发生的副作用不会随结果
丢弃而回滚；不可据此宣称跨模型调用的事务原子性。

## 4. SQL 执行接入与验证边界

SQL batch adapter 收集未跳过、未缓存的行；保持逐行参数的从左到右求值、
严格 NULL 短路、持久类型解码和既有逻辑类型身份。普通 SQL 标量路径不变。
批量接口仍借用同步输入，adapter 持有载荷副本，避免后续参数求值复用缓冲区。
成功标记只在整次 SQL 批量求值成功后发布。

2026-09-09 检查点：SDK 测试与严格 Clippy、C/Rust 布局、loader 白盒及实际
Rust 动态库测试、生产构建/链接、完整 kernel 和 23 项 CTest 已通过。
`rust_function_batch_fixture.h` 使用正常解析、类型推导、复制、预处理和代码
生成，将四种函数表达式放入 6、3、1031 行的 frame，覆盖原生批量函数、旧
服务回退、逻辑类型转换、NULL/空串/Unicode/内嵌 NUL、跳过/缓存/重新启用、
结果所有权和不重复绑定。后续分块非法 UTF-8、已部分缓存后失败、调用前取消
及宿主已接收两个结果后的取消，都清空整批结果的有效标记，lease 回收到零。

这仍是手供输入的真实 SQL frame 与动态库测试，不是实库扫描、恢复、全部
计划执行模式或模型吞吐证明。函数参数子树和 cast/type 包装层的批量接线
见第 6 节，其余消费链不能据此视为全部批量化。多参数严格函数的实际 Rust
纵向样例见下一节；真实 SQL 写入、网络副作用和异步任务的组合仍需继续验证。

SQL adapter 现在同时按 1024 个实际输入行与 64 MiB 输入载荷分块。严格 NULL
短路的行不占插件输入名额，NULL 值和空串仍是有效行，但不占载荷字节。
同一缓冲区的重复别名按每次传输分别计费，不因地址相同绕过限制。

放不进当前块的下一行只准备一次，取得独立载荷副本后先交付当前块，再把
已准备的行移入下一块；不回退参数求值，不重复 cast，不重试失败的插件调用。
分块前已经完成的参数副作用不会因后续错误而撤销。单值超过 16 MiB、单行
合计超过 64 MiB 仍拒绝，不能把一个函数调用的参数拆成多行。

批次不再持有跨行的 TempAllocGuard，当前行取得副本后可在下一行准备时
重置临时 allocator；若外层表达式已经持有 guard，则继续遵守外层生命周期。
64 MiB 仍只是传输载荷预算，不是整个 SQL 的内存上限：当前块、预备下一行、
loader 转换/输出、表达式结果以及 descriptor 都可能同时占用内存。隐式
转换之后的膨胀和输出超限仍会报错，不通过执行后重试猜测安全批量大小；
输出预算协商和整体资源治理仍需继续实现。

字节分块的完整 kernel 已验证：五个各 16 MiB 的别名输入，加一个 NULL
与一个单字节值，形成 4 行/64 MiB 和 3 行/16 MiB+1 字节两次调用。原生
Rust 批量、带逻辑类型 cast、旧单行文本服务均成功；精确回调计数证明没有
重算预备行。运行期列 NULL 仍调用声明的 cast，不等同于编译期 typed NULL。
后续块非法 UTF-8 使整批结果失效且不重试；16 MiB+1 字节单值在进入函数前
报错。生产构建、23 项 CTest 与边界检查也通过，本轮未改变 C ABI/Rust 插件。

Rust 文本参考插件自 `rust-text-batch-v12` 起将原有 `seekdb_rust_char_count` 服务
升级为同时提供单行与批量入口；服务/SQL 对象身份和存储格式保持不变。
GIS 仍可使用 C++，不因框架及 SDK 使用 Rust 而要求重写算法。

## 5. 多参数函数与声明式 NULL 策略

`rust-text-multiarg-v13` 增加 `seekdb_rust_concat3(a,b,c)` 和
`seekdb_rust_concat3_called(a,b,c)`，两个 SQL 对象共享 `concat3` 服务。
前者设置 `NULL_PROPAGATING`，后者清除此属性。新能力完全在 Rust 插件中
声明、注册和实现，没有修改核心表达式 factory 或新增执行 ABI。

两者连接三段 UTF-8 字节，保留空串与内嵌 NUL，结果限制为 16 MiB。严格
函数按当前宿主契约从左向右准备参数，遇到 NULL 就返回 NULL，不计算后续
参数、不调用函数；非严格函数计算全部参数，插件验证非 NULL 参数后再决定
返回 NULL。此契约不代表完整复刻 PG 的参数求值规则，也不保证外部副作用回滚。

例如 `seekdb_rust_concat3(NULL, seekdb_rust_text(X'FF'), 'z')` 跳过非法 UTF-8
参数并返回 NULL，`seekdb_rust_concat3_called` 的对应调用则报错。若非法
参数位于 NULL 之前，严格函数也报错。函数仍必须处理直接 ABI 调用中的 NULL，
不能把 SQL 层短路当成裸指针接口的输入保证。

验证包括 8 个标量 SQL 场景、4 个新增 6/3/1031 行批量场景、整批严格 NULL
零回调、第三参数失败时的严格/非严格对照，以及实际函数/批量调用计数。
三参数重复列的大输入按每行 `2×4 MiB+1` 字节计费，9 行形成 7+2 两批；
`2×8 MiB+1` 的单个结果超过上限时不发出结果、不重试，SQL 有效标记清零。
Rust 单元测试、严格 Clippy、实际动态库完整 kernel 与 23 项 CTest 已通过。

插件当前共有 19 个服务和 23 个对象，build ID 为 `rust-text-multiarg-v13`。
使用匹配的 manifest 和动态库部署；已有持久格式版本没有变化。

## 6. 嵌套参数子树批量求值

普通函数现在按参数顺序调用子表达式的 `eval_batch`。初始跳过集合包含调用者
不需要的行与本函数已经缓存的行；严格函数每完成一个参数，就把该参数结果
为 NULL 的行加入集合，后续参数不再计算这些行。全部行被排除后立即停止，
不进入原生常量表达式的全跳过 dry-run。mask 使用独立存储，避免被子表达式
重置 SQL 临时 allocator 时破坏。

cast、类型值及编码包装层也批量计算源表达式，再复用原有逐值转换/codec
协议，因此 `char_count(CAST(concat3_called(...) AS rust_utf8))` 不会因经过
cast 而使内部函数退回单行入口。cast/codec 本身并没有新增批量 C ABI。
新增测试按 SQL 名分别记录父子批次，检查 6/3/1031 行中父子都走批量路径、
函数的逐行入口计数不增加，并继续检查缓存、跳过、严格 NULL、错误及 lease。

有一个明确保留的兼容路径：若参数仍由函数 extra-info 直接引用存储 decoder，
预计算在该参数之后停止。decoder 可能报错或把非 NULL 存储解码为 NULL，
不能越过它预执行后续参数。行参数准备继续完成这一后缀，不重复解码。

新函数绑定已把直接存储参数包装为 `PluginTypeValueExpr::DECODE`，函数本身
不再携带这些参数的 sparse decoder 元数据。每个包装节点先批量计算源值、
逐值解码并把结果写入 SQL frame，随后父函数根据解码结果处理 NULL，再计算
后续参数。父函数准备参数时读取缓存，不重复解码。节点与元数据先构建、校验
逻辑身份及 catalog epoch，成功后统一替换参数；表达式复制和再次类型推导
读取固定绑定，不重新选择实现。旧绑定的后缀回退仍保留，不声称被追溯改写。

新增真实 Rust 持久类型的 6/3/1031 行测试，覆盖直接 count 及严格/非严格
concat 的嵌套第三参数；检查显式节点、跳过/增量缓存、每个非 NULL 值一次
解码、后续函数批量入口、非法存储头失败时零后续函数调用及 lease 回收。
该 Rust codec 对合法非 NULL 输入不产生 NULL；decoder 主动返回 NULL 的
更强故障注入仍需单独验证，不能用 SQL NULL 输入测试替代。

批量推进以参数为阶段，不提供跨行外部副作用的固定执行顺序；错误不会撤销
已经执行的参数或模型请求。子表达式输出会保存在 SQL frame 中，输入分块
仍不等于整条表达式树的内存预算。完整生产构建、首轮和最终 kernel、23 项
CTest 及边界检查通过；比较/聚合等其余消费链、整体资源治理与实库/异步
副作用验证仍在完整目标内。

深层 planner/index、完整 catalog 事务、AI 异步资源调度、轻量化测量和跨平台
验证仍属于完整插件化目标，不被本批量协议替代。
