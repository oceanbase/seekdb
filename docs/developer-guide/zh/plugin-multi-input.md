# 自定义执行器的多输入 SQL 适配与 Rust 轮询投影

状态：物理执行代码已接入，生产构建、Rust 计划解析测试和完整 kernel
回归通过。本文不表示优化器已经可以生成任意多输入计划。

## 解除的限制

原有 custom executor C ABI / Rust Context 已提供 input_count、独立
input_schema(index) 和 next_input(index)，但 PluginCustomOp 只接受
一个 child，并始终读取编号 0。本次把实际 SQL 适配扩大为 0–64 个
child，每个输入有自己的列数、表达式、逻辑类型、NULL 和 codec。

PluginCustomSpec 保留已有扁平 input_* 数组，增加 input_offsets_：
非空时必须有 child_count+1 项、第一项为 0、最后一项等于扁平列数，
各段单调不减且最多 1024 列。相邻偏移相同表示一个零列输入，不表示
没有该输入；没有 child 时使用显式 [0]。零 child 与有零列行的 child
是不同的关系。

offsets 为空保留原有单 child 语义，不向多个 child 隐式广播同一布局。
分区布局要求 explicit_input=true；数组长度不一致、错误边界、单输入
超限或重复 child operator 指针在插件 cursor 创建前拒绝。普通 operator
open 仍遵循内核先打开 child 的顺序，这不承诺无效 spec 的 child.open
没有发生过；正常规划器需在建立执行树之前完成结构准入。

## schema、借用与资源

每个输入的 CustomLayout 拥有自己的 ID、数值表示、codec 和列描述，
整个 schema 数组在取行前建立。输出布局独立保存，不按任一 child 猜测。
全部输入描述完成校验后才创建插件游标。

取行根据 index 选择实际 child，再读取该 child 对应的扁平列范围。
数值 scratch 和 ABI value 数组只按最宽输入分配，LOB 临时 arena 在
每次输入回调复用，不为 64 个输入分别保留 16 MiB 行缓冲。各输入的
描述内存则随总列数增长，需要纳入后续 query resource accounting。

一行借用仍只持续到下一次宿主回调或本次 next 返回；换输入同样会使
旧借用失效。Rust 算法如需同时保留多行，必须先复制为 owned 数据。
输出继续先复制和验证，在 next 与取消检查成功后才发布 SQL Datum。

每个输入独立执行 LOB materialize/codec decode，输出使用自己的
codec encode；一个输入的 stored 标记不影响其他输入。输入行、逻辑
输出行和编码输出仍分别有原有大小限制。本协议没有引入跨线程共享
游标、异步 query 指针或插件内存沙箱。

## 重扫失败必须覆盖整棵输入树

ObOperator::rescan 先重扫 child，再进入 inner_rescan。原先只在
inner_rescan 设置失败状态，遇到中途 child 失败可能来不及执行。
PluginCustomOp 现在在调用基类 rescan 前就进入失败状态，只有所有
child 和插件游标重扫成功后才恢复。

取行和批量入口也先检查该状态，不能被基类的“此前已经 EOF”快捷路径
绕过。输入失败、部分重扫或取消后不能交付旧缓存行；成功重扫后重新
建立正常取行状态。关闭和 destroy 仍可释放失败游标及其模块 lease。

## Rust SMP1 参考算法

Rust candidate v7 的执行 service 增加插件私有的 SMP1 计划：四字节
magic、little-endian u32 输入数，再为每个输入保存输出列数及该输入
的列序号映射。计划最多 64 KiB、输入最多 64、每个映射最多 1024 项。
SPJ1 和空计划保留原来的单输入语义。

SMP1 在读取第一行前验证所有输入映射与输出 schema，包括最后一个和
完全为空的输入。schema 不匹配不能等读到该分支才发现；零列映射也
保留输入行数，不跳过宿主对未投影输入值的校验。

算法按 0、1、… 顺序轮询尚未结束的输入，每次取一行，投影并复制到
Rust 所有的缓冲；遇到 EOF 后不再重复读取该输入。各输入可以不同宽度，
有不同映射，但投影后的列必须符合共同输出 schema。行数、NULL、重复
投影和各输入的内部顺序被保留，不承诺全局排序。

缓存预算由全部输入共享，仍是 65536 行、约 16 MiB 的参考限制，不是
每个输入分别获得一份预算，也不是完整 spill 引擎。rescan 清理全部
已缓存行并重新读取所有输入。0 个输入的该参考算法返回空关系；其他
源算子可在同一执行协议内实现自己的行为。

## 验证与后续规划工作

Rust 单测覆盖不同分支边界、零输入/零列、64 输入、全部截断、尾随
字节、索引/列数/输入数/计划总长度超限。kernel 夹具使用实际 SQL
frame、PluginCustomOp、loader 和 Rust DSO，子行与物理 spec 明确由
测试构造，覆盖混合宽度、重复投影、零列、空分支、0/64 输入、总列数
超过 1024 但每个输入合法、不同输入 codec、部分重扫失败、输入失败、
取消与最后分支的非法映射在取行前拒绝。最新执行结果见实施进度。

后续工作区已增加 v3 计划片段请求，开始将多个 PlanId 与逐输入依赖
接入 builder、分配、裁剪和 codegen，并分开目标关系与实际输入属性。
新接线已通过完整 kernel 的两输入逻辑夹具和正常 SQL 单输入纵向
用例，多输入 SQL 联动仍待验证，详见[计划片段](plugin-plan-fragments.md)。
物理执行的本检查点不作为后来规划器改动通过验证的证据。

完整 SQL 验收还应让规划回调真正提交多输入请求，经优化器选择、分配、
裁剪和 codegen 后运行 Rust 算法，并同时保留未选中候选不被修改、
跨分支错误依赖拒绝和多输入重扫的断言。当前十组物理夹具不能替代
这一条验证链。

多输入物理适配是这条路径的必要执行基础，不是将完整目标缩减为一个
轮询合并样例。缓存/PX 重绑定、类型/索引/恢复、实库 catalog 以及 AI
资源和轻量化目标仍保留。
