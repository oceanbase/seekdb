# Namespace fork 最小原型验证方案

日期：2026-09-14。状态：最小原型已实现，普通表 2/20 表夹具、关闭开关的对照、独立向量夹具已通过。实测记录与复现命令见 [namespace_fork_prototype_results.md](namespace_fork_prototype_results.md)。原定首轮投入上限为 3 人日，不是完整功能的完工估计。

本文描述 V1；后续实现与验收见 [内核 V2](namespace_fork_kernel_v2.md)。

统一设计仍以 [namespace_fork_design.md](/home/nijia.nj/.codex/worktrees/af63/seekdb_for_codex/docs/research/namespace_fork_design.md) 为准。本文缩小实验范围，不改变已定架构，不替 D1 选择门禁/回滚策略。

## 1. 只回答一个核心问题

能否在真实 seekdb 中，创建时不遍历用户表、不创建目标用户 tablet、不复制用户数据、不触发 fork 主动 freeze，随后在首次访问时基于同一个旧快照建立目标表，立即完成独立读写？

实验采用单进程、固定表结构、单代分支。以两个普通 database 承载 A/B 的用户表；新表继续使用现有全局唯一 table/tablet ID。分支定位由实验驱动显式完成，不改 SQL 名称解析或所有存储对象键。这里的 database 是实验容器，不能据此宣称 namespace 的字典、权限和 SQL 状态已隔离。

真实 MVCC、目标 memtable、来源基线读取、事务提交均使用现有引擎。原型新增的是捕获与延迟建表的衔接，不另写内存数据库模拟这些行为。

## 2. 最有价值的范围缩减

| 完整设计中的工作 | 首轮实验做法 | 本轮证据边界 |
| --- | --- | --- |
| 固定 namespace 的 SQL 进程 + IPC | 一个现有 seekdb 进程，普通 MySQL 连接 | 不验证 SQL-only 启停、进程隔离或 IPC |
| 完整对象键及分支 catalog | database 隔开名称，目标表使用新 ID | 不验证保留局部 ID、独立权限、DDL/DCL |
| 持久 COW 目录与 StorageView 引用图 | 小型运行时分支记录，来源结构固定 | 不验证目录持久化、COW、精确对象保留 |
| namespace 快照引用及 GC | 复用一条覆盖所有本地 tablet 的粗粒度快照保护 | 仅在专用实验实例中使用；保护范围过宽，来源必须存活 |
| 按需物化 | 首次访问一张表时调用现有单表 fork helper，显式传入捕获的 S | 可以检验延迟创建后的真实旧版本读取与独立写入 |
| 不因 fork 提前 freeze | 用已有 DEBUG_SYNC 将 fork 后台任务停在主动 freeze 之前 | 证明前台路径不依赖该阶段；不验证正常转储交接协议 |

实现限定为非分区普通表，恰好两列整数 `id`、`v`，`id` 为主键，无二级索引、LOB、外键、触发器、自增、生成列。来源在实验中允许 DML，结构和对象集合保持不变；测试额外创建晚到表以检查拒绝路径。暂不做源删除、多代 fork、merge、进程重启及持久分支恢复。

## 3. 复用点与第一个停止条件

已核对当前工作区 `dbe8fcdbb2ed` 的代码：

- [fork_single_table_in_trans_](/data/1/nijia.nj/seekdb-fork-落地/src/rootserver/fork_table/ob_fork_table_service.cpp:41) 接受 `fork_snapshot_version`，可复用目标 schema/tablet 创建和 fork 读取绑定。现有普通 `FORK TABLE` 会重新取点，实验不能直接逐次调用它来冒充统一旧快照。
- [is_snapshot_related_to_tablet](/data/1/nijia.nj/seekdb-fork-落地/src/storage/compaction/ob_freeze_info_mgr.cpp:293) 将 `tablet_id=0` 的快照关联到全部本地 tablet，并参与多版本保留计算。
- [batch_add_snapshot](/data/1/nijia.nj/seekdb-fork-落地/src/share/ob_snapshot_table_proxy.cpp:161) 在现有事务中协调快照 GC 水位并校验新快照。应通过该管理路径登记保护，不让 Python 直接拼 SQL 修改系统表。
- [try_update_info](/data/1/nijia.nj/seekdb-fork-落地/src/storage/compaction/ob_freeze_info_mgr.cpp:488) 将快照保护与回收水位装入存储侧。写入系统表成功不能代替对这条生效路径的核对。
- 已有 [fork_snapshot_lifecycle.py](/home/nijia.nj/.codex/worktrees/af63/seekdb_for_codex/tools/obtest/fork_snapshot_lifecycle.py) 用 `FORK_TABLE_WAIT_FREEZE_END` 暂停后台后验证真实 DML，可复用其驱动方式。旧实验不是延迟创建目标表的证据。

**先验证粗粒度保护，再接延迟建表。** 小实验要确认保护在发布分支前有效，并且来源发生后续提交、经历正常回收更新后，未访问的表仍能按 S 读取。不能通过增大 undo retention、关闭全局 GC 或把所有表预先打开来使它通过。

还需处理一个明确的接口差别：稍后首次访问时，S 可能已经早于当前“允许新申请快照”的水位。此时应使用一直有效的原保护，不能重新按新快照申请 S，也不能删除现有有效性校验来接受任意旧 SCN。延迟 helper 的实验入口必须验证分支记录、来源身份和原保护仍有效。底层可见性检查保持。

如果这个衔接要求重写 GC、日志回收或加入完整持久目录，首轮在此停止，报告具体缺口。实测已确认新快照 GC 水位超过 S 后，既有保护参与存储侧保留边界计算，延迟创建的表仍能读取 S；没有覆盖物理版本淘汰后的长期恢复。

## 4. 原型执行路径

运行时只记录 `目标 database ID -> {来源 database ID, S, 固定 schema 版本}`，最多 8 条，保护通过类型和 S 定位。记录在引擎中；已物化表从目标现有 schema 查询，不维护第二份集合。对象集合固定，不在捕获时生成全表映射。

### 捕获 A 到 B

1. 通过开关和专用库名前缀识别实验，校验来源 database 身份，取一次合法快照 S。捕获不检查每张表的结构，结构限制在首次物化时校验。
2. 在现有元信息事务中创建空目标 database、登记粗粒度保护。捕获不调用现有 `obtain_snapshot(data_table_schemas)` 的逐表收集路径。
3. 确认保护的生效协议，发布运行时分支记录。失败不返回有效句柄；已提交但尚未就绪的资源由实验清理流程负责，不伪装成回滚成功。
4. 返回 B 的实验句柄。此时目标用户表/tablet 数为零。

### 首次访问 B.t1

1. 驱动显式请求 `ensure_table(B, t1)`。通过固定来源身份取得该表定义，校验属于允许的夹具及原保护有效。
2. 调用 `fork_single_table_in_trans_(..., S, ...)`，复用现有目标建表、MDS 和 schema 发布。为该表建立 B 自己的实体，其基线仍是 A@S。
3. fork 后台任务由预先设置的 DEBUG_SYNC 停在主动 freeze 前。驱动检查暂停成功，不能等任务完成后再称为首次可读。
4. 用普通 SQL 查询/修改 B.t1。后续访问复用同一个目标表。

同一表的物化由实验驱动串行，暂不建设通用并发物化管理器。目标业务事务涉及多张表时，在 `BEGIN` 前显式完成这些表的准备，避免把内部建表隐式提交混进业务事务。

实现沿已有 `FORK DATABASE`/`FORK TABLE` 入口分流，复用 SQL 语法。进程环境变量 `SEEKDB_NAMESPACE_FORK_PROTOTYPE=1` 且目标库名前缀为 `__fork_proto_b` 时进入实验路径；捕获来源须以 `__fork_proto_a` 开头，延迟物化还须匹配已登记的来源/目标 ID。关闭开关时走现有实现。`ensure_table` 是 Python 驱动的显式准备步骤，不是 SQL 自动名称解析功能。

### 生命周期

只允许一个隔离实例内的短期实验会话。来源表、保护和实验句柄在本轮结束前存活。引擎重启后运行时记录失效，驱动必须拒绝续用，不能仅凭残留 database 名称重建分支身份。

结束时停止新的实验请求，等待在途 SQL 结束，再停止本轮拥有的 seekdb 进程；后台因 DEBUG_SYNC 无法及时退出时终止进程并等待回收。保留带 PROTOTYPE 标记的日志和压缩数据归档用于排查，不作为可重开的分支持久化结果。无需在首轮实现在线解除全部引用及恢复孤儿状态的产品协议，也不能声称这些已通过。

## 5. 最小功能验收

夹具预先建好 t1、t2。t1 含确认为未转储的已提交数据；t2 是稍后才访问的表。数据量以人工可核对为准。

| 操作 | 必须看到的结果 |
| --- | --- |
| 事务 1 同时修改 A.t1/A.t2，保持未提交；捕获 B；随后提交事务 1 | B 两张表都看不到这次晚提交，不能出现只带入一半的结果 |
| 捕获后只访问 B.t1 | 只创建对应目标用户表/tablet；B.t2 仍未创建 |
| 捕获后 A.t2 更新、删除、插入，经过实际回收状态更新后再首次访问 B.t2 | B.t2 仍准确读取 S 时的内容 |
| B.t1 独立更新、删除、插入；再做一次回滚 | A 不变，B 的提交生效、回滚不生效 |
| 重复访问 B.t1 | 不重复建表，不重新取得基线快照 |
| fork 后台停在主动 freeze 前 | 查询和 DML 已完成；目标尚未依赖后台整表构建结果 |

用代码落点计数和系统状态检查工作量：捕获前后的实际单表物化 helper、tablet 收集 helper 调用计数都为 0；目标用户表和 fork 任务均为 0。结合捕获路径检查，确认它没有枚举来源用户表、创建用户 tablet、复制用户行或派发逐表 fork 任务。计数器不是对全引擎所有复制/freeze 操作的通用统计器。

可用 2 张与 20 张预建普通表各走一次相同断言，确认捕获没有藏入逐表处理；这只是有限夹具下的功能证据，复杂度结论还要结合代码路径。不新增吞吐、CPU、内存、IPC 或启动耗时 benchmark，不承诺毫秒级返回。首次查询明确记录发生了哪些建表/提交/读取步骤。

## 6. 向量索引单独做一个小实验

向量部分用现有单表 fork，暂不接入上面的延迟多表原型。直接复用 [fork_table_vector.test](/data/1/nijia.nj/seekdb-fork-落地/tools/deploy/mysql_test/test_suite/fork_table/t/fork_table_vector.test) 的建表和查询方式，但要确认使用的索引维护模式；无明确异步模式证据的测试不能当成异步索引验收。

只选两个已知输入状态：有可复用持久图且少量增量；没有可复用持久图、主要为增量。用实际索引状态判断夹具是否就绪，不靠固定 sleep 假定完成。

在第一次目标查询前暂停 fork 后台主动 freeze，检查目标查询是否成功、执行计划是否实际用了 ANN，以及装载路径是否读取持久图、补增量或等待其他步骤。用小型无距离并列的向量夹具检查快照内容、删除与分支修改；精确查询帮助核对数据，ANN 的一般正确性不以任意数据上 top-k 必须与精确结果完全一致为判据。

若只有释放暂停、后台完成后才成功，就把结果记为“已有表级路径依赖后台阶段”，不要解除暂停后改记快速可用通过。该实验只查首次查询的功能依赖与工作来源，不证明大图装载很快，不实现图共享/分代，也不解决 D1 的局部门禁互等。

## 7. 投入顺序与交付

首轮建议以 3 人日为投入上限，顺序执行：

1. 先用不超过半天核对并做粗粒度保护的小验证，得到可继续或具体停止原因。
2. 通过后完成捕获、指定 S 的延迟单表物化及上述普通表验收。这是主要交付。
3. 剩余时间做向量小实验和整理证据；超出上限时向量结果标未完成，不扩成索引重构。

预计新增代码集中在 fork 服务的实验分流/运行时记录、原有 helper 的受保护旧快照接入及一个 Python 驱动。后台暂停使用已有 DEBUG_SYNC。若实现开始扩散到 SQL 全局状态、通用 IPC、存储键或恢复格式，说明已经超出本原型范围。

已提供入口命令 `python3 tools/obtest/namespace_fork_prototype.py --binary build_release/src/observer/seekdb`。结果输出捕获/物化状态、S、真实查询结果、任务状态和工作计数，遇到不满足断言时退出失败。使用本地构建缓存，独占自己的实例、端口与目录。

当前工作区即可开展普通表原型；源删除不在范围，因此无需为开工移植旧分支的 v2 源删除实现。旧 worktree 的二进制可用于已有路径的辅助实验，但不能拿它验证新加的捕获/物化逻辑。

最终报告只给出普通表核心假设是否成立、向量首次查询暴露的依赖，以及下一项必须解决的缺口。通过本轮仍不能宣称完整 namespace、生产 GC/恢复、SQL 进程拆分或快速 ANN 已经可行并验证。
