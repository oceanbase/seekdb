# 设计修订：统一 Runtime，用独立内部 Namespace 承载实例管理表

> 2026-09-29：用户已明确拒绝新增完整 Runtime 的资源成本。本方案撤回，不以资源测量或未来优化为条件继续推进。当前硬约束与候选方案见 [复用现有执行环境](design-table-ownership-existing-runtime.md)。下文仅供追溯。

状态：修订设计，尚未实现。2026-09-29。本文替代 `design-table-ownership.md` 的独立实例 SQL 上下文方案。文档和测试留在本地，不提交分支。

## 1. 为什么撤回上一版

上一版拟为实例 SQL 单独装配固定 schema、精简缓存和部分执行服务。当前 SQL 仍有大量 NamespaceRuntime 和全局服务依赖，无法通过列举几个接口证明实例 SQL 路径完整。之后每新增服务都需要判断是否装配、采用什么配置、是否支持实例上下文，形成第二套持续维护的执行环境。

本次撤回独立的 InstanceSqlRuntime、INSTANCE SqlTarget、实例专用 schema guard 和精简服务配置。内部 SQL 与用户 SQL 均使用现有 Namespace 执行模型。资源优化对所有 Namespace 采用相同机制。

## 2. 选择的方案

保留一个只供实例内部使用的 Namespace，承载实例管理表。它使用普通 NamespaceRuntime、普通 SchemaService、普通 SQL proxy 和普通物理 tablet 编码；全套服务由同一装配流程管理。

Namespace 1 可作为该内部 Namespace，其身份只在 bootstrap 组合处确定并注入依赖。它有完整的 Namespace 基础内表（包括服务正常运行需要的本地状态表），另有实例管理表。默认用户 Namespace 和用户模板采用独立的初始 schema/data，父链从创建时就与内部 Namespace 分开。

实例管理表在业务含义上属于实例；内部 Namespace 是它们共用的 SQL/schema/存储容器。它的生命周期与实例相同，登录、fork 和删除权限由管理策略控制。普通请求执行中没有“实例表”服务分支。

示意：

```text
实例
  内部 Namespace（例如 ID 1）
    标准 Runtime + 标准基础内表 + 实例管理表
    parent = 0；普通客户端不可登录；不能作为 fork 源

  用户模板 Namespace（独立初始化，parent = 0）
    标准 Runtime + 用户空间所需基础内表/初始数据
    可以作为 fork 源
       └─ 默认用户 Namespace
            └─ 用户 fork 的 Namespace
```

以上 ID 仅内部空间保留 1；用户模板和默认用户空间的 ID 由启动分配流程确定，不让正常请求依赖固定数字。

## 3. 为什么不会继承实例表

`__fork_proto_meta` 的库/表/列/索引等记录只存在于内部 Namespace 的原生 `__all_*` 中。其数据 tablet 也只存在于该 Namespace 的物理地址域。

用户模板通过原生空空间初始化产生，不能通过 fork 内部 Namespace 再删除控制库来构造。用户空间从该模板 fork，父链只能经过用户模板和其他允许 fork 的 Namespace。

因此，控制库记录不会出现在用户 `__all_*` 的数据源里，父链也不可能探测到内部 Namespace 的物理 tablet。不需要 schema 装载过滤、表名黑名单、特殊实例地址域或读路由排除表。

管理策略在创建父子关系之前检查 fork 源是否允许被继承，并在恢复注册信息时校验该约束。策略使用持久化的访问/fork 属性，不在正常 scan/DML 中判断 ns_id==1。用户能修改的 SQL 字段不能改变这些管理属性。

## 4. 普通执行完全一致

每个 proxy 仍固定绑定一个 Namespace：

```text
用户模块 ──> 所属 Namespace 的 proxy ──> 所属 Runtime
实例管理模块 ──> 注入的内部 Namespace proxy ──> 内部 Runtime
                                                   ↓
                                      同一 SQL 与物理执行实现
```

`target_namespace`、session 的 NamespaceRuntime 绑定、schema 服务选择、plan/PS cache、事务与锁全部沿用统一机制。不需要给每个服务增加 INSTANCE 支持，也不将内部 Namespace 的服务作为任何用户请求的默认回退。

bootstrap 将内部 Namespace 的 proxy/schema 等依赖传给管理模块。后台任务持有明确的 owner，生命周期由实例管理。禁止在普通模块新增无目标 `get_instance()` 或直接查 ns1 补全依赖。

现有尚未归属明确的全局服务仍需按已确认的 Namespace 架构继续清理；本方案不会自动使它们正确，也不新增第二种 SQL 执行上下文来适配这些遗留服务。

## 5. 表归属如何表达

表归属决定创建位置和调用方应使用哪个已存在的 Namespace SQL client：

- Namespace 业务表及本地服务状态，在所属空间创建/访问。
- 实例管理表，在内部 Namespace 创建/访问。
- 索引、LOB 等依赖对象通过普通 DDL 跟随主表。
- 混合实例和 Namespace 状态的内表需要按数据生命周期拆分，不能单凭名字或当前使用的 proxy 分类。

内表初始化清单声明哪些表在所有空间建立、哪些实例管理表只在内部空间建立。这是按表的数据归属配置，集中在 bootstrap；所有空间的服务类型和初始化配置模式保持一致。内部空间自身也需要正常 Runtime 所依赖的基础表，不能通过删掉基础表间接迫使各服务适配特殊模式。

公开实例信息仍通过明确的系统视图/虚拟表访问入口提供，其实现注入内部读取能力并执行权限检查。不会让每个用户 SchemaService 自动回退到内部空间查表，也不把内部库的所有定义挂载到用户目录。新增具体公开表时同时定义其可见范围、写入权限和事务语义。

## 6. bootstrap 改造是关键工作

当前控制表创建与 Namespace 1 用户空间、template fork 混在一起，需要分成可验证步骤：

1. 按现有原生 bootstrap 创建内部 Namespace 的标准基础 schema、数据和 Runtime；在其中建立实例管理表及 Namespace 注册记录。
2. 抽取可复用的“从内置定义初始化空 Namespace”流程。该流程创建标准基础元数据、初始用户/权限/系统变量并发布 schema，不继承另一个 Namespace 的物理快照。
3. 用该流程创建用户模板，标记 parent=0，并在实例管理表中原子发布 ready 状态。构造期间对用户不可用；失败重启后可恢复或清理，不能把半初始化模板发布为可 fork 源。
4. 从用户模板创建默认用户 Namespace。普通客户端默认登录该空间；显式请求内部 Namespace 时检查管理访问策略。
5. 内部 Runtime 与用户 Runtime 采用同一套服务装配和启动/停止流程。启动分阶段所需的控制依赖显式传入，不能用访问 ns1 的隐式回退解决启动循环。

这里需要真实的空空间初始化能力。仅修改父链为 0 而继续复用内部空间的 `__all_*` tablet，会破坏隔离；不能作为实现捷径。

## 7. 资源成本

本方案接受增加一个标准 Runtime 容器的固定开销。当前 Namespace 1 同时承载默认用户数据与实例控制表；分离后需要分别持有这两份状态。复用现有用户模板后，目标是相对当前结构增加一份 Runtime，不随用户 Namespace 数量额外复制实例执行环境。

不能同时声称“与普通 Namespace 完全一样”又保证“只有几 KB”。已有缓存桶、内存上下文和后台定时器都有实际成本，需测量启动后空闲开销和控制 SQL 的峰值。

若该固定成本不可接受，优化对象是通用 NamespaceRuntime 的初始化和资源策略：例如缓存按实际使用增长、统一的空闲容量策略、线程执行资源复用。相同规则适用于全部 Namespace，不设置 internal_ns 专属桶数、不维护实例服务开关清单。是否需要这项优化由测量决定，不把未实现的优化计入本方案收益。

完整服务实现仍只有一套。以后新增服务按正常 Namespace 装配即可覆盖内部空间，无需再评估某个精简执行环境的接口完整性。新服务自身需要的通用基础表也走统一初始化；实例管理数据归属仍通过依赖注入明确表达。

## 8. 事务、物理地址与后台操作

- 控制表管理事务在内部 Namespace 的标准 SQL client 上执行，使用普通事务/锁能力。
- 需要与用户 DDL 共同原子提交的操作必须逐项审计：如果现有代码本来复用同一事务，保留明确的跨内部 client 事务附着与锁释放；不能因为物理位置隔离而新增不受控的两次提交。已有两阶段发布协议保持其恢复条件。
- 物理 ID 继续统一编码 Namespace ID 与 local tablet ID。存储层只接收物理 ID 和快照，不认识内部空间的策略。
- 用户 Namespace DROP/GC 不得删除内部空间。内部空间的保留、登录和 fork 限制由管理属性与权限控制；只在管理入口检查。
- 现有物理 owner 推断中的无来源默认 ns1、以及按库名返回 GLOBAL 的路径仍需清理。控制表按所属 Namespace 走标准映射即可。

## 9. 用户可见变化和边界

默认用户数据不再属于 Namespace 1。普通客户端登录入口仍可保留默认空间名称，但底层绑定到独立用户 Namespace；现有显式连接 ns1 的测试和工具需要更新。

用户空间的 SHOW、名字解析、`__all_database` 和 `__all_table` 都不会出现控制库；内部授权入口可以正常看到其持久化记录及完整 schema，二者的数据源各自一致。

内部 Namespace 不能作为 fork 源。这是在管理命令入口的一条策略，而非正常 SQL 路径的服务或 schema 特判。若用户要求 Namespace 1 必须继续兼任可 fork 的默认用户空间，则本方案不成立，不能再用加载时过滤弥补。

本版本仍不考虑旧数据升级兼容。不公开用户任意创建实例级表或切换表归属的语法。

## 10. 实施与验证

实施顺序：抽取独立空空间 bootstrap → 分开内部空间和用户模板/默认空间 → 注入控制表所属 proxy → 删除名字过滤/GLOBAL→ns1 特例 → 审计其他实例表。

四件套至少覆盖：

1. 内部空间及默认用户空间、两个子空间和一个孙空间：控制 schema 记录只存在于内部空间，所有公开查询入口一致。
2. 普通客户端不能绑定内部空间；fork/drop 管理命令拒绝不允许的源/目标；内部授权 client 正常查询、修改控制表。
3. 用户模板 parent=0，所有用户父链均不经过内部空间；父链解析和 COW 使用普通逻辑。
4. 用户空间与内部空间相同逻辑 table/tablet ID 不串数据、schema、plan/PS cache 和锁。
5. bootstrap 中断、模板初始化失败、fork 提交前后重启：无半初始化空间对外发布，无丢失 pin/引用，无已发布 Namespace ID 重用。
6. 原有用户 DDL、DML、索引/LOB 和后台归属用例通过；控制操作事务回滚和重启恢复完整。
7. 测量分离前后的空闲内存、线程数量、控制 SQL 延迟和并发峰值，明确固定额外 Runtime 的成本。
