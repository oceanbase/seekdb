# tablet物化重构：架构评估

日期：2026-10-02。核对基线：`50557ddbe3f3956afa2b71addbfcf15d380738d6`。

状态：方案 A 已以 `a9bf8740a` 为基线实施完成，并提交推送 `a73ae2b0c`。下文保留静态评估结论，阶段代码与失败/验证记录见 [实施记录](tablet-materialization-progress.md)。文档保留本地，不提交分支。

基线说明：以下调用点和成本分析基于 `50557ddbe`。其中“物理创建与 KV owned 分两次提交、失败后补登”已经由后续提交 `a9bf8740a` 消除；不要把这些描述当作当前状态，也不要把这部分删除计入未来物化入口重构的收益。详见 [事务共用实现核对](assessment-shared-transaction.md#0-当前实现核对a9bf8740a)。该变化不影响本评估对只读备库、源依赖、估算和基线调度的判断。

用户的判断标准：**更少的代码、更统一的入口和实现**。资源成本也是取舍因素，但不能只列性能代价而忽略简化收益。不得用增加包装层、隐藏原有多套实现来冒充完成重构。

## 1. 结论

首次实际访问即创建本地物理 tablet 有明确的局部收益：主库的正常访问可以始终交给本地 tablet，由其 `fork_info` 处理继承数据；创建检查可以统一。

但当前代码不支持“只把首次读也改为创建，就能消除多数 fork 特殊处理”的结论：

1. 尚未访问的 tablet 仍存在。首次创建、历史对象回收仍须使用父链、fork SCN、生命周期检查、墓碑和 pin。
2. 本地 tablet 的行读取能够沿源链读取，但统计估算和部分 MDS 元数据读取没有同等的继承语义。创建一个本地对象不能自动让这些操作统一。
3. 尚未接管的 tablet 仍需要源读取、多来源快照和基线任务；这些实现不会因首次访问创建而消失。
4. 备库可能首次访问一个主库尚未物化的 tablet。当前持久化创建要求可写，不能直接在只读备库执行。若主库创建、备库保留继承读，两套读取准备实现仍要存在；若引入本机临时对象，则新增了对象生存期和回放协调协议。
5. 当前物化会自动进入基线调度。首次读创建会扩大接管、源转储及可能重写的数据范围。要只支付创建成本，需要另行定义接管调度策略。

**当前建议：先以统一的 Namespace tablet 访问实现为重构方向，保留读取继承、修改时创建的策略。首次访问一律持久化创建暂不作为既定目标。** 两个方向都需要集中 schema/LOB 绑定、来源解析、创建和访问保护；这一部分的收益不能全部归给“读也创建”。

原始评估阶段没有实现候选补丁，未承诺净减少多少行。下文分别列出删除候选、必须保留的实现和新增责任，没有把调用点数量当作可直接删除的数量。当前方案 A 已完成本地四件套及最终差分审查；生产代码新增 662 行、删除 630 行，净增 32 行，收益是统一实现及补齐保护，不宣称净减少代码。用户要求记录的结论不变：先统一访问实现，保留读取继承、修改时物化；首次读强制持久化仍未成为设计目标。事务共用的独立评估及已提交实现见 [事务共用](assessment-shared-transaction.md)。

## 2. 当前状态模型与创建成本

| 状态 | 本地物理 tablet | 读取继承数据 | 需要保留源对象 |
| --- | --- | --- | --- |
| 未物化 | 无 | Namespace 来源解析后读祖先 | 是 |
| 已物化、基线未完成 | 有 | 本地增量加源 tablet 的 fork 快照 | 是 |
| 基线完成 | 有 | 自己的 SSTable 集合及块引用 | 不再因这个子副本的读取依赖源对象；其他引用另算 |

首次访问创建只使被访问对象从第一行进入第二行；保留 O(1) 的 Namespace fork，就不能消除第一行。读写仍共享第三列中已有的继承行读取机制；数据块可以在完成接管后继续共享。

直接创建副本的 3 处带 schema 调用：写批次、建索引 helper、截断分区分支。AccessService 的无 schema `ensure_tablet` 不能独立完成新副本创建；当前工厂在缺少绑定 schema 时会返回 `OB_NOT_SUPPORTED`。因此，“把所有调用移到最底层 get_tablet”会重新引入存储向 Namespace SchemaService 的反向依赖，不能作为统一入口方案。

### 两种方案都能获得的删除收益

- 建索引和截断分区中重复的 schema/LOB 收集、转换、创建循环，可交给实际操作的公共准备实现。
- Native/Fork 的写物化策略类可以评估由同一实现替代：现有物理对象直接使用；缺失对象根据明确的 Namespace 元数据判断是否允许创建。
- 散落的物理 ID 编码、来源查找、快照限制可在访问模块内部共用。
- 下层 AccessService 的 Namespace 来源解析和创建钩子可在调用方全部迁入后移除，访问保护的持有期必须一起迁移。

这些收益来自统一实现，A、B 两个方案都可以取得。保留一份公共解析器属于必要语义，复制出多份按调用方分类的解析器才是应删除的重复实现。

### 首次访问创建独有的收益

- 主库已成功打开的 tablet 永远有本地物理身份，普通行扫描不再把整个扫描重定向到父 tablet。
- 直接继承读取的 SCN 限制可交给本地 tablet 内部的源读取上下文。
- 某些后续物理操作不用区分“本地无对象”和“本地有对象”。这一收益仅适用于确实在公共打开之后执行的操作，不涵盖 GC、探测及首次打开之前的优化器操作。

### 首次访问创建仍须保留的实现

- 工厂和 GC 使用的父链/历史解析、墓碑、生命周期判断。
- `fork_info`、源 tablet 读取、多来源快照上下文、源 MemTable/SSTable 访问。
- 基线复用/重写/安装、源转储等待、完成标记及恢复。
- 未访问对象和未完成基线对象的引用保护、全局 pin 的现有保留范围。
- 创建与 owned 双提交及补登，除非独立完成“事务共用”。

## 4. 为什么“本地 tablet 已存在”还不足以统一全部操作

### 4.1 行读取已经支持继承，估算实现并未完整支持

[ObTablet::auto_get_read_tables](../../src/storage/tablet/ob_tablet.cpp)（2880 起）会把源读取表与本地增量组合；[ObMultipleMerge::build_extra_access_ctx](../../src/storage/access/ob_multiple_merge.cpp)（184 起）为各物理来源设置 fork 快照。这些是已物化但未完成基线时仍必须存在的代码。

但 [ObLSTabletService::estimate_row_count](../../src/storage/ls/ob_ls_tablet_service.cpp)（4962 起）获取读取表后，把它们放进 `ObTableEstimateBaseInput`。该结构不携带各来源的 fork SCN；[MemTable 估算](../../src/storage/access/ob_table_estimator.cpp)（189 起）只传入 tx_id 和范围。宏块/行数统计（LS tablet service 5036 起）还会直接累计 MemTable 物理行数与 SSTable 的统计。

所以，首读前先创建本地 tablet，并不会自动消除“父在 fork 后的行也可能影响估算”的限制。要删掉现有继承态估算分支，必须先给估算定义正确的继承语义，或明确返回不可用估算。本轮是静态结论，没有新增动态正确性缺陷判定。

### 4.2 物化没有把父的全部 MDS 元数据复制成孩子的本地状态

当前物化明确复制了自增序列，但并非完整复制所有 MDS 状态。`ObTablet::read_truncate_info_array`（887 起）读取本 tablet 的缓存/MDS，没有沿 `fork_info` 自动读取源的逻辑。表级 fork helper 的 `copy_tablet_truncate_info_` 仍需要解析历史来源并限定 SCN。

这意味着“任何操作只拿孩子的物理 tablet 即可”的承诺还需要增加元数据继承或复制实现。不能把所有来源解析调用都计作可删除行数。具体每类 MDS 的继承策略应由物理语义决定，不把 Namespace 判断下沉到 MDS。

### 4.3 首次读创建与只读备库

构造场景：主库 fork C，但从未访问 C 的 T；备库已经回放到这次 fork，首次查询 C.T。备库有祖先数据和 Namespace 元数据，但没有 C.T 的本地物理 tablet。

当前 [ObTransService::get_write_store_ctx](../../src/storage/tx/ob_trans_service_v4.cpp)（721 起）在 `server_is_write_enabled()` 为 false 时返回 `OB_STANDBY_DATABASE_READ_ONLY`；持久化创建和 owned 登记需要写入。

可选补充方案及代价：

| 补充方案 | 对“统一、少代码”的影响 |
| --- | --- |
| 主库首读创建，备库继续继承读 | 必须保留直接继承读实现，并新增角色策略；不能承诺只有一种访问准备 |
| 备库请求主库创建后等待回放 | 引入网络请求、等待协议及主库不可用时的处理，不再能仅凭本地已回放快照完成首次读 |
| 主库 fork 时就创建全部子 tablet | 改变 fork 成本为随 tablet 数量增长，违背当前不枚举全量 tablet 的目标 |
| 备库创建本机临时子对象 | 需要区别临时/持久对象，并协调后续主库 CREATE 回放、切主和对象回收；本轮不把它当作已有能力 |

这不表示 Namespace 架构无法支持备库；它说明“每次首次读都必须先持久化创建”的新前提会增加额外设计工作。

### 4.4 接管调度与后台探测

[普通合并调度](../../src/storage/compaction/ob_tablet_scheduler.cpp)（965）会调用 `schedule_baseline`；[基线调度实现](../../src/rootserver/fork_table/namespace_fork_kernel_prototype.cpp)（1239 起）按 fork 未完成标记安排任务，并可推动源的未完成基线。扩大物化范围会直接扩大这个调度集合。

此外，IVF 的缓存失效检查、GC 和大合并进度检查不是“开始使用新对象”。当前 [大合并进度](../../src/rootserver/freeze/ob_major_merge_scheduler.cpp)（402 起）只检查 owned tablet。若所有枚举/探测都隐式创建，周期任务可能物化整个 Namespace；若保留只读探测接口，则“一个入口供所有 get_tablet 使用”也不是准确的目标。

后台由物理 tablet 枚举驱动的转储/合并仍只能看到已经存在的对象。若要求后台主动创建所有继承对象，需要新增 Namespace/schema 枚举，工作量与资源增长均应单列。

## 5. 候选方案比较

| 项目 | A：统一访问实现，保留按修改需要创建 | B：统一访问实现，首次实际访问都创建 |
| --- | --- | --- |
| 普通行读取 | 公共准备实现返回物理来源和受限快照；已有本地对象走其 fork 读 | 公共准备实现先创建本地对象，随后走其 fork 读 |
| 读写/DDL 的调用方是否需自己判断物化 | 不需要 | 不需要 |
| 来源解析、创建、schema/LOB 绑定是否能共用 | 能 | 能 |
| 未访问对象的历史解析和回收 | 保留 | 保留 |
| 已物化但未接管的源读取实现 | 保留 | 保留 |
| 备库首次读 | 可继续只读解析，无需本地持久化 | 需要上节中的补充方案 |
| 首次扫描很多分区 | 不因纯读增加本地 tablet | 对访问到的绑定单元创建本地 tablet，并进入当前接管调度 |
| 状态数 | 未物化、未接管、已接管 | 仍有这三种，只是访问过的对象更早进入后两种 |
| 主要新增责任 | 公共准备和调用方迁移；保持保护周期和 schema 来源 | A 的工作，加只读角色、读触发接管策略、更多首次创建入口及其 schema/锁依赖 |
| 本轮判断 | 收敛收益明确，可作为下一步实现方向 | 主库行读取更统一，但尚未证明总体代码更少；当前不推荐直接实施 |

fork 时创建全部子 tablet 能进一步消除“无本地对象”状态，但会使 fork 枚举和创建全部对象；作为边界对照即可，不列为当前推荐候选。先创建可丢弃的内存视图、写时再持久化是另一种更大改造，不能把它与当前持久化物化混为一谈。

## 6. 统一实现应该具体做到什么

建议将 seam 放在已有 Namespace 逻辑访问与共享物理存储之间，不新增承载一整套服务的 Runtime，不让共享 LS/tablet/MDS 反向找 Namespace 服务。

### 6.1 调用方提供什么

- 显式所属 Namespace/存储作用域、逻辑对象和当前操作上下文。
- 已固定版本的 schema；绑定 schema 由同一实现从该版本的 guard 收集，不在低层全局查找。
- 已有的读写/元数据操作语义、快照与截止时间。不要引入按 SQL 语法名称列举的物化白名单。

### 6.2 模块内部共用什么

1. 校验身份与对象生命周期，计算本地物理 ID。
2. 使用同一历史解析器确定源和 SCN；获取并持有访问保护。
3. 实际修改需要本地副本时，由同一工厂准备主/LOB 绑定并创建。
4. 生成内部的物理访问上下文，并由扫描/修改入口消费它；调用方不再手工做编码、检查 owned、限制 SCN、调用 ensure。
5. 保护持续到扫描关闭、写入/元数据操作结束，保证 GC 的排空语义。不能准备完成即释放保护。

“统一入口”表示所有逻辑 tablet 访问使用同一个准备实现；不要求把扫描、创建、删除和 GC 探测硬塞成一个带大量布尔参数的方法。GC 和来源工厂必须保留无副作用的状态查询。底层已拿到物理 ID 的回放、转储、合并不再次进入 Namespace 打开流程。

具体迁移顺序可为：统一绑定准备 → 统一读写访问准备 → 接入实际 MDS/DDL 修改入口 → 迁入估算、范围与逻辑后台入口 → 核对全部调用方后删除 AccessService 的 Namespace 准备钩子和 DDL 提前物化 helper。每步用删除清单验收，不只新增新接口。

### 6.3 无论选 A/B 都不能遗漏的约束

- 内表 schema 装载本身会走 SQL 读取。`namespace_inprocess_scan_service.ipp` 和 `namespace_inprocess_scan_schema.ipp` 已显式携带 schema 防止重新进入正在装载的 SchemaService。新入口须继续接收已准备的布局，避免“读 schema → 创建 → 再读 schema”的递归。
- 元数据修改准备要在正确的锁阶段执行。不能把当前 DDL 事务前的物化直接移到持有事务锁后的通用 get_tablet。
- 主/LOB 辅助对象必须作为绑定单元处理，不能因先读到辅助表而建立不完整副本。
- 首次打开、fork、DROP/TRUNCATE、GC 交错时，来源快照及逻辑出生边界不变。
- 不因首读创建就放宽 snapshot pin，也不以 owned 代替基线完成。
- 整表锁与未来新建副本的冲突覆盖是独立问题，首次打开策略不自动解决它。

## 10. 完整设计决定：共享来源清单、批量可达性回收与接管释放

日期：2026-10-08。状态：§§10–11 本轮范围已于 2026-10-09 完成，结项与逐项证据见 source-tree-progress.md，第 9 节是前期已运行的验证。本节取代讨论中“必须逐个登记所有孩子才能做 GC”“先逐条登记再改共享清单”的建议，也不将第 9 节的定向通过扩大为整套设计已经验证。

### 10.1 目标和明确取舍

- Namespace fork 的元数据工作量不随 tablet 数量线性增长；8000 分区不在 fork 请求中复制 8000 条依赖。
- 父 Namespace、父表或其当前 schema 删除，不改变孩子已获得的数据视图。
- 精确保留到实际物理来源，取消 Namespace pin 以 `tablet_id=0` 长期保护全部本地 tablet 的方式。
- 接管复用现有 SSTable clone/rewrite、tablet table-store 安装和宏块引用机制。接管完成的对象不再要求父 tablet 存活。
- 不维护持久化的“物理 tablet → 全部 Namespace 使用者”索引。采用批量可达性遍历生成本轮按 tablet 的保留计划，接受 GC 的批量扫描成本。
- 存储层不认识 Namespace；合并、GC 和接管不隐式激活 Namespace 的整套 SQL 服务。
- 普通用户只读不能成为永久不推进接管的原因；通过有预算的后台物化和接管推进。接受由此逐渐增加孩子物理元数据及必要重写 IO 的成本，不声称只读孩子永远零物理对象。
- 无升级兼容要求，实施与验收使用新初始化的数据目录，不保留旧例外表与新清单两套权威。

这里的“精确”是排除未被引用的来源，不承诺现有 MVCC 回收会只留下离散快照的最少版本集合。接管前仍可能保留来源 tablet 在最早所需快照之后的中间版本；缩短接管前阶段解决其长期成本。

### 10.2 两层权威，不新增第三套块引用

1. **实例 KV 中的逻辑来源图**：回答某个 Namespace 视图下，逻辑 tablet 的数据从哪里来、以什么快照读取。DDL、fork、物化和 Namespace 删除通过同一模块更新它。
2. **每个实例本地的物理状态**：包括 tablet 的创建代次、未完成 fork 的源 ID/快照、接管完成标记、table store 和宏块引用。回答本机能否直接读取孩子、是否仍需源物理对象。

同一份逻辑来源图在主备复制；物理接管可以在主备分别推进。主库的本地完成标记不得被翻译成一个让所有备库立即释放来源的 KV 标记。

已接管孩子引用的 SSTable/宏块仍由原生存储引用机制保护。这里不再添加 Namespace 宏块引用计数器，也不把引用计数的内存值当成唯一持久化事实。

### 10.3 持久化结构

存放在 InstanceMetaStore 的实例级 KV collection，归上层目录模块维护；不放进可继承的 Namespace SQL 表。

| 记录 | 内容及职责 |
| --- | --- |
| Namespace 记录 | 名称、状态、访问属性、当前视图根、已提交 schema 版本；父名称/ID 仅供来源展示，读路径不依赖父 Runtime 存活 |
| 视图根 | 一对一致的 table-definition 根和 tablet-source 根，加边上的快照上限；一个事务发布 |
| 不可变树页 | 对象查找、子页引用及 cap；写时复制，只修改必要路径 |
| table-definition 条目 | raw table ID、不可变物理创建描述引用及主/LOB/索引关联；完整 SQL schema 仍在 Namespace 系统表 |
| tablet-source 条目 | logical tablet ID、raw table ID、物理来源身份；来源身份包含物理 tablet ID 和创建代次，避免把重建的同 ID 对象当成旧来源 |
| 物理创建描述 | 从 DDL 已确定的表定义生成，包含物化需要的 storage schema、表类型、主辅绑定等；按表的版本共享，不在 8000 个分区条目中重复序列化完整表定义 |
| GC 运行状态 | 本机任务进度/临时工作集，不参与主备复制；可丢弃并重算，不作为数据存在性的唯一事实 |

当前 `NamespaceCatalogTree` 已有不可变页、查找、插入、删除及 `cap` 传播；`InstanceNamespaceMetadata::collect_unreachable_pages()` 也已有从 Namespace/snapshot 根出发的元数据页可达性回收。复用这些实现，补齐物理来源创建代次、有效快照归并、物理保留计划和并发回收协议，而非另写一棵树或宣称遍历从未实现。不能直接把当前未用于生产来源路由的树宣布为完整实现；`exceptions + parent-chain` 会被统一的来源图替换，不再同时维护两份路由权威。历史退役原因及新增门禁见 10.13。

所有 Namespace 所属物理表都要进入清单，包括系统表、schema 表、主表、索引、LOB 辅表等。InstanceMetaStore 自己属于实例存储，由实例模块维护，不进入 Namespace 来源图，避免目录读取递归依赖自己。

物理创建描述只承担按指定视图准备物化/接管参数的职责。本方案不声称同时解决此前独立讨论的“全局 freeze SCN 与各 Namespace schema 版本对应”问题；大合并的 schema 版本选择仍是单列设计事项，不能因为这里新增描述就默认正确。

**cap 规则：** 路径上已有 cap 与 fork 快照取最小值。fork 只给共享根加 cap，不展开叶子。孩子写入后替换相关叶子为本地物理来源，新叶子不受旧 fork cap 限制；未改变的兄弟子树保留原来的 cap。多代 fork 通过持久化树边计算快照，不沿在线 Namespace 服务查找。

### 10.4 fork、DDL、物化、删除分别做什么

**fork：** 在一致发布边界取得来源视图根及快照 S；同一 KV 事务插入孩子和共享根引用。成功发布前已经建立 GC 可见的保护。无需遍历 tablet 或装载孩子服务。新创建的孩子指向来源的固定清单版本，父后续 DDL 不会改变它。

**DDL：** 在原有 SQL 元数据事务提交前，将该事务确定的对象变化提交给目录模块，用已有 attach 能力写 table-definition/tablet-source 及新根；由同一个原生事务提交。新增/替换物理对象的持久化身份也必须随其对应的 DDL 阶段一起发布。

- 改名等不改变物理布局的操作无需更新 tablet-source。
- 加列等改变物理创建描述的操作更新表级描述，尽量共享原 tablet 子树，不逐分区复制完整 schema。
- TRUNCATE/重定义等替换 tablet 的操作发布新来源；旧树仍被快照或读者引用时继续保留旧来源。
- 多阶段 DDL 不强行变成一笔覆盖整个建索引/数据回填过程的巨型事务；每个已对外发布的阶段，其 SQL 元数据和目录变化必须原子一致。
- 新入口收敛到 schema 元数据事务拥有者及物理对象生命周期，而不是逐条 SQL 语法加钩子。没有目录更新的受管物理创建/替换不得发布为可用状态；bootstrap 也走同一描述生成与登记逻辑。
- 删除当前依靠“DDL 提交后读新旧 schema 再差异发布”的双提交流程及对应补发布状态；业务 DDL 任务自身的恢复仍按原有阶段保留。

**首次写/后台物化：** 读取所属视图中的物理创建描述，复用已实现的物化内部共用事务。创建主/LOB 等绑定单元及本地 tablet 后，用本地物理来源替换当前视图条目。物化后的 tablet 自身持久化未完成 fork 边，继续保护其源。不能因为逻辑清单已指向孩子就释放父数据。

**接管：** 按原有 freeze/dump、clone/rewrite、table-store 安装流程执行。安装完成前保留原来源；成功持久化 complete 后，本机后续依赖遍历不再沿该 fork 边。正在使用旧 tablet 版本的读取/任务仍持有原生 handle，允许它们结束。完成到释放无需再提交一笔复制的 Namespace KV 状态。

**DROP/TRUNCATE 与 Namespace 删除：** 删除当前视图的条目/根并关闭新请求准入；已有快照根不变。逻辑删除、持久化对象回收分离。空壳转换之前仍需依赖判断，不能先清空 table store 再检查孩子是否引用。

### 10.5 GC 不查询“谁”，而是批量标出“还要什么”

选择可达性回收，不给每次 fork 增加逐 tablet 反向登记。

一轮任务的输入包括：所有有效 Namespace 视图根、仍被后代引用的固定视图、已开始读取或尚未提交目录操作持有的根，以及本机原生事务/任务保护。显式命名快照若后续增加，也必须通过同一个根持有接口纳入。

视图选择与根保护必须同时发生：RC 请求持有语句需要的根，固定事务快照的请求持有该快照对应的根到事务结束；旧计划/DDL 任务也要持有其使用的版本。不能只登记已经拿到物理 tablet handle 的读者，遗漏“事务已取得旧快照、稍后才第一次打开该表”的情况。选择旧视图须来自已持有的事务/快照根，不能在 GC 截点之后凭裸 SCN 重新引入未受保护的历史来源。

遍历形成两类结果：

1. 可达目录页和物理创建描述：防止回收孩子仍使用的清单/schema 描述。
2. 按物理对象身份归并的保留请求：对象必须存在；若是固定视图则保留其有效快照；若对象本机接管未完成，再沿其物理 fork 边补上源对象及源快照。已有 complete 的孩子停止沿父边遍历。

例如 B 的旧清单引用 P@S，另一个当前空间使用 Q，遍历结果只给 P 增加历史 S 的要求，不给 Q 加 S。多个使用者需要 P@S、P@T 时，现有存储回收接口可以先取较小者，无须保存使用者名单。

共享页按页 ID 归并，cap 取所有到达路径的最小值再向下传播。树页采用严格无环引用，页在孩子之后创建；批量工作集可以按拓扑顺序处理，避免每个 Namespace 重扫完全相同的子树。page ID 是内容哈希，不能按 ID 大小推断创建时间或拓扑顺序。物理 fork 边同样必须无环；发现损坏则本轮不执行受影响对象的破坏性回收并报出原因。

这不是每回收一个 tablet 就重新遍历所有 Namespace：每轮批量构建一次保留计划，然后按 tablet 批量交给回收/合并任务。工作集只在本轮存在，有明确内存限额。按用户最新决定，本轮不实现临时文件或外排序；超出预算时不发布不完整计划，保留现有安全保护，并记录回收无法推进的限制。有实际规模证据后再评估扩展，不能把这种资源优化作为本轮完成的前提。

### 10.6 GC 与并发 fork/DDL 的一致性

仅扫描一遍根还不够，必须定义该轮计划的有效范围。

1. fork 获取 S 到提交根引用、DDL/物化的来源图发布，都进入统一的短期发布协调接口。
2. GC 在该接口建立一个一致截点 C：等待已经取得旧 fork 快照却尚未发布的操作结束，取得目录事务快照和当时的根集合，并登记本轮保护。随后立即释放发布协调，不在整个遍历期间阻塞 fork/DDL。
3. 截点前删除、但仍有读者持有的旧根作为根集合的一部分保留。新开始的读取从已发布根取得来源，并在物理对象锁下获取读 handle；物理回收使用同一对象身份校验和保护机制，不等待所有 Namespace 的长查询结束。
4. 截点后的新 fork 取得的 S 不早于 C；当前视图叶子在本轮至少保留到 C。若新 fork 继承更早 cap，该更早依赖已经属于截点时可达的旧树路径。禁止无已有引用凭空重新挂接一个任意旧根。
5. 截点后新建的目录页/物理对象不在本轮候选范围内。目录候选页来自截点目录事务快照，不能用内容哈希 page ID 的数值上限表示创建边界；后续删除还须受上述发布协调及禁止重新挂接未保护旧根的规则约束。新对象回滚等特殊原生生命周期仍由原生事务规则负责。
6. 计划有效期持续覆盖使用它的合并/回收任务；任务结束才释放本轮保护。超时取消任务，未完成对象留给下一轮，不沿用失效计划。提交删除前还需原生物理身份及活跃 handle 检查。

这里的 C 是一次 GC/合并任务的有限期安全边界，不是每个孩子永久持有的全局历史 pin。截点后不阻塞普通业务写入；原生行版本、事务快照和活跃读取保护仍然参与最终最小保留边界。

从当前全局 pin 切换时，必须先使新图和新 GC 协议可恢复、可回放，再删除旧入口。没有“图查不到就退回 Namespace 1”或长期保留全局 pin 掩盖缺失条目的分支。

### 10.7 后台推进：只读孩子与资源预算

新增的职责是补齐“逻辑继承但没有孩子物理对象”这一段，复用现有接管后半段。

- 主库的目录维护任务从有效清单中选择尚依赖可写来源的条目，分批调用物化接口；不需要客户端写入。
- 接管任务只读取物理创建描述和原生 tablet，不启动 Namespace SQL 服务。当前依赖完整 ObTableSchema/SQL proxy 的物化创建接口需要下沉为显式物理创建参数；这是实施工作，不是假定现成。
- 物化内部事务继续使用现有原生事务能力。仍需内部连接的创建/序列/映射适配器由组合层显式注入，不能在缺少服务时回退 Namespace 1，也不额外创建一套实例 SQL Runtime。将来完全移除内部 SQL 不是本项完成的前提。
- 优先推进阻碍删除的来源、很老的快照和历史增长明显的来源，同时为普通依赖保留公平队列，避免只读孩子永久饥饿。
- 限制并发、每轮 tablet 数量、重写字节和 IO；进度来源于持久化来源图与 tablet fork 状态，崩溃后可重建，避免另外维护一份容易失配的任务权威。
- 一旦所有相关条目不再沿父物理来源读取，其历史保护自然从下一轮可达图中消失，无需“所有孩子都完成”的全局计数。
- 仍需永久保留的模板初始数据不会凭空消失；目标是消除对持续变化的父对象的依赖及多余历史，而非让数据本身不占空间。

需要接受的负载边界：若持续创建快照/孩子的数据量超过可用接管带宽，依赖和空间会积压。达到资源预算时限制新 fork 或明确拒绝，不能通过提前回收仍被使用的数据解决。具体默认预算是部署参数，不改变引用协议。

### 10.8 主备与恢复

- 来源树、Namespace 根、物理创建描述和原生物化事务随同一 LS 日志复制。备库按一个已可读的回放边界取得根与物理状态，不拼接不同进度。
- 不可达目录页的 KV 删除由主库执行并复制；备库不独立修改复制目录。目录读取使用视图所持有的 KV 快照；选择根的短事务结束前，保护移交给独立的 KV 快照句柄，句柄不占用原生事务描述符或目录 GC 准入计数。旧页的逻辑 DELETE 可以复制，旧读者仍按受保护 SCN 读取历史版本；本机 GC 复制根工作集时也复制该句柄。KV 合并保留边界同时受现有读者和原生弱读水位约束，避免尚未开始的新弱读取得已经被回收的版本。物理来源及宏块的 GC 则由各实例根据本机根保护、读取及接管状态决定。
- 备库不为逻辑上尚未物化的孩子自行执行新的元数据写事务；由主库后台物化并复制 CREATE/目录结果，升主后由新主继续推进。
- 已回放创建的孩子 tablet，可以在本机执行原生基线接管。每台实例根据自己的持久化 complete 标记生成 GC 计划。主库 complete、备库 incomplete 时，备库继续保护父来源。
- 本地 slog/检查点恢复 table store 和 complete 状态后，才允许 GC 使用它解除来源保护。来源树恢复、原生未决事务收尾和回放可读边界均就绪后再启动破坏性回收。
- 初始全量物理拷贝必须把来源图和该拷贝截点仍需要的本机物理对象作为一致集合，并在文件传输期间持有原生快照/块引用保护。不能只复制逻辑上的当前 Namespace 清单，也不能在拷贝期间让发送端回收尚未传完的来源。
- 新的源副本若来自不同主备实例，重新生成本机可达性计划，不复制另一实例的临时 GC 计划或接管任务队列。

### 10.9 模板与初始化

模板仍通过 fork 构造，复用现有初始化结果。创建后在开放用户入口前，完整执行模板所需系统表/基础数据的物化与接管，不能只处理用户表；模板自己的来源条目随后全部指向其物理对象，GC 不再需要初始化空间的旧数据来维持模板。

模板必须有可供内部生命周期使用的身份；禁止登录是显式访问属性，不再通过跳过 Runtime 注册实现。后台物理维护不因此启动其整套 SQL 服务。

首次安装失败直接报失败，由用户重新安装；删除 `__template_build__` 清理用户对象、重命名及补建恢复链。正常运行的已提交 DDL/引用恢复继续存在，但不为首次安装半成品增加专门补救机制。

该流程首次初始化会支付基础系统数据的接管成本；后续创建空 Namespace 仍只 fork 已准备好的模板。默认空间和模板具体 ID 由 bootstrap 组合层分配与绑定，不在正常请求引入 `ns == 1` 特判。

### 10.10 复杂度、内存与 8000 分区

| 操作 | 预期成本与限制 |
| --- | --- |
| fork | 固定数量根/Namespace 记录的事务；不遍历 8000 个分区，不创建 8000 个孩子 tablet |
| 查找一个来源 | 树高范围内的 KV 页读取，路径上传递 cap；不装载整棵树或所有 schema |
| 修改一个来源 | 复制受影响树路径；8000 分区中修改一个分区不复制全表清单 |
| 更新表的物理描述 | 表级不可变描述加一个根路径更新；不把完整表 schema 存 8000 份 |
| 截断/重定义整个分区表 | 若本身替换全部 tablet，仍有 O(N) 物理创建/条目变化，不能宣称由共享清单消除 |
| GC 一轮 | 与实际访问的共享树页、边、来源和候选物理对象有关；共享节点归并，不能保证常数时间。工作集有内存预算，分批遍历；最终保留清单暂存内存，超限不发布不完整计划。临时文件暂缓 |
| 主动接管所有分区 | 最终可能创建 8000 个孩子物理 tablet；这是完成独立接管的元数据成本，不由首次 fork 同步承担 |
| 多个不同快照的重写 | 可以产生新的数据块与 IO，现有 clone 只能复用符合条件的数据；不承诺每次 fork 永远零拷贝 |

不把“元数据不复制”说成“无元数据增长”。长期增长由实际清单分歧、活跃快照和孩子物理对象数量决定；本设计不额外为每个 Namespace 常驻一份完整清单缓存。

### 10.11 实施顺序与退出标准

| 阶段 | 内容 | 完成标准 |
| --- | --- | --- |
| 1 | 固化来源身份、COW cap 规则、表级物理创建描述；将受管 DDL 阶段接入 SQL/KV 共用事务 | 普通/分区/索引/LOB/系统表变化与新根同事务；故障时不存在 SQL 和来源目录两份权威分叉 |
| 2 | 用共享清单接管 fork/读路由/物化/删除，统一根持有接口 | 8000 分区 fork 不全量登记；多代 fork 和父 TRUNCATE/DROP 保持视图；删除旧 exception/父链权威 |
| 3 | 本机可达性 GC、C 截点及任务保护；主备本地 fork 边纳入 | 无关 tablet 不受老快照保护；并发新 fork/DDL/读取不能被误删；取消全局 Namespace pin |
| 4 | 不依赖 SQL Runtime 的后台物化与接管；接管后保护自然消失 | 无用户写入的孩子也能公平推进；来源对象及历史版本最终可回收；内存/IO 有预算 |
| 5 | 模板初始化简化、备库初始拷贝/角色切换及压力验收 | 模板不长期保护可写父快照；慢备库不会因主库完成而提前 GC；重启恢复幂等 |

实施分步可构建、可测试，但在阶段 3 前不对外宣称已解决精确保留，在阶段 4 前不宣称解决只读孩子的长期依赖。无升级兼容需求，不为过渡期旧数据保留永久双轨逻辑。

### 10.12 必须进入本地四件套的验收

1. 8000 分区，连续 fork 多个孩子：记录 fork 新增 KV 行/页数和延迟、物理 tablet 数量；验证未发生随分区数线性复制。修改单分区检查 COW 路径放大。
2. 固定老快照下持续更新无关表：验证它的实际历史回收推进，不只观察某个全局水位数字。
3. 同一来源被两个快照引用：一个完成接管/删除，另一个继续读；两者均释放后，来源及最终共享块按原生回收规则释放。
4. A→B→C，多代物化交错；父 DROP/TRUNCATE、同名重建、旧 ID 未决创建回滚，不读取错误代次。
5. GC 捕获 C 的前后并发 fork、DDL 提交/回滚、DROP 和长读，含已取 S 未提交 fork；故障点证明无少保护窗口。
6. 已有 `fork_detached_restart_probe.py` 两场景保留，扩展所有关联对象与整 Namespace 系统表接管；pin/来源释放之前后强制退出，不能仅靠新登录补修复后才通过。
7. 无客户端写入的孩子，后台完成所需接管且未激活整套 SQL Runtime；任务限速和大分区内存上限可观测。
8. 主库先 complete、备库后 complete；分别回收及重启；备库初始拷贝期间来源删除；升主后继续推进。主库完成不得导致备库读丢数据。
9. 首次模板初始化失败明确失败；正常模板通过 fork+接管形成，随后父空间持续写入不受模板旧快照约束。
10. 全文、向量、LOB、分区索引及物理 schema 描述一致性分别覆盖。第 9 节通过不替代这些尚未执行的验收。

以上是本轮验收范围，生产实现已分阶段进入分支；各项实际证据与尚未通过的门禁见 source-tree-progress.md，不把设计条目直接视为已通过。

### 10.13 树实现的历史及复用约束（2026-10-08 核实补充）

- `f736de6fd2066331fcf76f0738af0de354fd89c5`（2026-09-14）即 `Prototype kernel namespace fork with persistent COW catalog and lazy tablets`。当时已有 catalog/directory 双根、持久化 pages、COW put/find、fork 根共享和快照 cap；不是本轮首次提出或首次实现树。
- `bd1a46a57a5deb4c5757f13260d5b88fd06383d0`（2026-09-21）切换 exception-table model，主要正常读写路由改为父链加 owned/tombstone，停止 catalog/directory 树写入。该提交的 `docs/research/namespace_worker_functional_delivery.md` 保存了当时的决策和测量。
- 历史测量：某个约 6000 schema 对象的实例 pages 有 38503 行；手动执行 150 轮 GC 后剩 2669 行，记录称约 93% 是不可达旧页。FANOUT=8、树高 4～5、逐对象登记复制路径、GC 仅手动触发且每轮最多 256 页共同造成积压。该数据是当时实验结果，不是本轮基线新测值。
- 当时选择例外表，是为了去掉逐表登记和页垃圾开销，利用确定性物理 ID 沿父链探测来源；不是证明持久化树不适用于 fork。最初还收紧过父 Namespace 删除语义，之后才另行补回允许删除及历史来源保护。
- `4d7509e6602fbf4355077d6b07567bcea5173bf5`（2026-09-24）将现有树抽到 `src/namespace/catalog.*`，属于代码移动。当前生产源码中树的直接调用集中在 `collect_unreachable_pages()`；正常来源路由仍走例外和父链。

因此本设计不是恢复第一版原样。实施增加三个必过门禁：

1. DDL 批量变更使用批量树编辑，在一个事务内合并公共路径，不能为同一批 8000 条目逐条发布中间根并持久化整条重复路径。发布最终根前不可见的新页尽量在事务内合并生成。
2. 对有限批次的创建/物化/删除，记录新增页、最终可达页、不可达页和后台回收进度；自动 GC 在停止变更后必须追平，不能依赖人工重复触发。持续超过 GC 带宽时需要预算约束，不能宣称采用 COW 就没有垃圾。
3. 用 8000 分区和历史约 6000 schema 对象两个负载核对页大小、扇出、写放大与内存。扇出按页字节预算和实际条目大小选择，不能仅把 FANOUT=8 改成 128 就宣称解决，也不能重复保存完整 SQL schema 导致元数据体积膨胀。

最终取舍仍是共享清单，但复用范围比先前表述更大；真正新增工作是事务接入、完整来源语义、自动且并发安全的物理保留/回收，以及只读接管推进。

## 11. 整体目标与暂缓范围（2026-10-08 用户确认）

本轮主题：完成 Namespace fork 的来源定位、数据依赖、接管与回收改造。§11.1 核心目标已完成，结项与验收证据见 source-tree-progress.md；§11.3 为明确暂缓范围。用户明确将内存来源视图和树节点缓存列为后续性能优化，当前不实施。

### 11.1 核心目标

1. **fork 后视图稳定。** 孩子记录固定来源根及 fork SCN；父 DROP/TRUNCATE、同名重建乃至 Namespace 删除不改变孩子原有视图。来源身份须区分物理对象代次，不能仅探测父当前同 ID 对象。
2. **fork 不逐 tablet 复制。** 实例 KV 保存共享 COW 清单；fork 只增加固定数量的根引用和 Namespace 元数据。table-definition 与 tablet-source 分开组织，物理创建描述按表版本共享；不为 8000 个分区复制 8000 份完整 schema。
3. **统一来源权威。** fork、访问解析、DDL、物化、删除和 GC 使用同一来源图，最终移除 exception + 父链路由。完整 SQL schema 继续放在 Namespace 系统表；来源图不成为另一套完整 SQL schema。
4. **元数据原子发布。** 每个 DDL 发布阶段的 SQL 元数据、来源变更和树根在同一原生事务内提交。物化复用已完成的共用事务基础，不能出现物理对象与来源登记各自提交的可见窗口。
5. **仅保护实际依赖。** 每轮从有效根及活跃请求/事务保护出发，批量汇总物理来源及历史 SCN 需求。逐步替换 tablet_id=0 的 Namespace 长期全局 pin；不维护来源到所有 Namespace 的持久化反向名单。与并发 fork/DDL、旧读者和原生回收保护共同保证安全。
6. **只读孩子也能解除父依赖。** 物化是创建孩子物理 tablet；接管是让它的数据访问不再依赖父 tablet。后台按预算推进二者，复用原生 SSTable clone/rewrite、table store 和块引用。接管完成后，共享数据块仍由原生引用保护，不等于必须复制全部数据。
7. **主备分别判断物理依赖。** 逻辑来源和物化事务随 LS 复制；接管完成状态按本机持久化结果判断。主库完成不能释放备库尚需的父来源，重启、全量拷贝与升主均需保持该规则。
8. **模板成为可独立维护的数据来源。** 初始化通过 fork 创建模板，再完成所需物化与接管；禁止用户登录以明确属性表达。后台维护不装载整套 Namespace SQL Runtime；首次安装失败直接失败，不增加补建修复链。

### 11.2 本轮必须面对的成本

- 正确性基线允许来源解析逐层读取 KV，不宣称 DML 已做到零额外 KV 读取；高频点查的附加开销保留为明确的性能风险。
- COW 路径写放大、批量 DDL 合并路径、合理页容量和自动页 GC 属于基础方案要求，不能重现旧版本仅靠手工回收的积压。
- 只读孩子后台独立接管会逐渐增加物理 tablet 元数据，并在必要时重写数据；限制内存、并发及 IO。
- 没有新增存储引擎或块引用体系；存储层仍接收物理身份及 SCN，不理解 Namespace。

### 11.3 暂缓项

- **GC 临时文件/外排序（用户明确暂缓）。** 当前不新增临时文件索引、外排序或磁盘查询路径；有实际规模和内存证据后再评估。优先正确性闭环与简单分批遍历，最终清单保留在内存。当前 262144 项上限超限会保守拒绝新计划，可能导致大图回收长期不推进，此限制不能隐瞒；紧凑容器优化也不作为接管闭环的前置任务。

- **来源查询内存优化（本次明确暂缓）。** Namespace 内存视图保存根；不可变树页按需装载、跨视图共享并限制内存；一次访问持有解析结果。目标是热路径零额外来源 KV 读取，冷缺页才读 KV。提交/回放发布、与 schema/事务视图一致性、旧根生命周期须一起设计，不能仅添加一个无版本映射缓存。此项不阻塞基础正确性实现，也不代表用户接受最终性能退化。
- **首次读也自动物化。** 不作为此次数据引用方案的前提，仍是先前 tablet 物化重构的独立取舍；本轮通过后台预算推进只读孩子。
- **全局 freeze 与 Namespace schema 版本、大合并按 SCN 取物理 schema。** 继续作为独立技术方案；本轮的物理创建描述不解决该问题。
- **更广的实例内表分类、实例管理 SQL、实例私有存储和配置重构。** 不并入本轮来源与回收改造。
